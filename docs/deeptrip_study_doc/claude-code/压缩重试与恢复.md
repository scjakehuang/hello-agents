# Claude Code 2.1.307：压缩重试、尾部保留与熔断源码笔记

本笔记只根据本地发行包恢复的 JavaScript 做静态核对，没有运行目标、请求模型或修改 recovered。行号对应 `readable/` 下 Prettier 排版文件；混淆名是发行代码中的真实名字，中文含义是解释名。

## 1. 一条实际调用链

`chunk-hkcbd84t.js:6734 pu` 是主查询 async generator；在每轮请求前 `:7063` 调用 `P.autocompact`，默认依赖 `:5989` 对应 `exr`。请求因过长/媒体失败且不需要工具后续时，进入 `:9140–9359` 的响应式恢复。

响应式链路：

```text
pu 收到被暂扣的 prompt-too-long / media error
  -> kvo 尝试消费正在生成或已就绪的预计算摘要
  -> CWn 运行策略/Hook，判断能否复用；否则新压缩
     -> gvo 托管进度/遥测
        -> $ve 负责选择摘要分组、保留尾部、缩短输入重试
           -> vur 请求模型只输出摘要
        -> jRr 将成功结果封装为新的上下文
  -> 新上下文再次进入主查询
```

若 `!tN()`，`pu:9252` 还存在 `Al` 旧路径。不能把所有安装环境都描述为永远同一条恢复路径。

## 2. 真正的分组单位：不是固定保留 N 条消息

`chunk-wvsyb4fb.js:102136 gpt` 先 `Is(messages)`，过滤 `type=progress`，然后交给 `:102114 a2`。

`a2` 的顺序规则：

1. 虚拟 user/assistant（`Gk`）直接放当前组，不触发分组；`Gk` 定义在 `chunk-s7k1n636.js:2662`，检查 `isVirtual === true`。
2. 当前消息是 assistant，`message.id` 不同于上一次 assistant id，且不是 `resumedFromIncompleteThinking`，且当前组非空，才结束当前组并以此消息开新组。
3. 同一个 assistant message id 的流式分块、它的 tool_result、到下个 assistant 出现前的消息都在一组。

例如（由代码推演的人工样例，不是运行结果）：

```text
U1, A1(text,id=m1), A1(tool,id=m1), tool_result1, U2, A2(id=m2), tool_result2, U3
    ↓
G0=[U1]
G1=[A1(text), A1(tool), tool_result1, U2]
G2=[A2, tool_result2, U3]
```

默认保留最后一组意味着保留整个 G2；不是“最后一个用户问题”，也不是“最近 10 条”。这种分组通常让同一响应及其工具结果一起移动，但 `a2` 没有逐个比较 `tool_use.id` 与 `tool_result.tool_use_id`，不能说它对任意损坏历史都提供工具配对修复保证。

`tOs:102140` 用 `gpt(messages).length < 2` 判断没有可压缩的多组内容。主循环 `pu:9169–9208` 在符合恢复条件但不足两组时直接把错误展示给用户，并说明请求开销可能来自固定前缀；不会无休止总结同一条消息。

## 3. 响应式算法 $ve 的状态与初始化

`chunk-wvsyb4fb.js:102900 $ve`：

| 变量 | 含义 | 初始化 |
|---|---|---|
| `s` | `gpt` 后的分组 | 计算一次 |
| `w` | 总组数 | `s.length` |
| `be` | 从尾部保留多少组 | 默认 `1` |
| `we` | 逻辑摘要尝试计数 | `0` |
| `Me` | 是否剥离媒体 | `false` |
| `Ge` | 最后兜底状态 | `null` 表示按组阶梯模式 |
| `Ee` | 每组 token 估算数组 | 懒计算 `s.map(Og)` |
| `Ye` | 是否已尝试仅总结开场组 | `false` |

当 `keepNoRound === true`、最后组没有 `Xpt` 判定的人类 queued command，且 `rAo()` 为真时，`be=w`，直接进入更激进的兜底策略。`rAo` 在 `chunk-ywba0mfz.js:2133` 返回远程旗标 `tengu_hidden_frog`（本地缺省 true），实际运行值不能仅靠包确认。

默认最后兜底可用条件：`allowFallback !== false && rAo()`。调用者会根据阻塞程度、媒体错误、classifier overflow 等决定 `allowLastResort`，不能脱离入口只说“总会截断历史”。

已知道主请求超量 `initialTokenGap` 且 `w>3` 时，先减最后一组估计 tokens；若剩余差额仍大于零，用后述 `edn` 先扩大保留组数，减少第一轮必然过长的摘要请求（`:102927` 附近）。

## 4. 阶梯模式：越旧的内容送摘要，越新的整组保留

`$ve:102949` 每次循环：

```js
summarizeEnd = max(0, groups.length - preserveGroupCount)
toSummarize = groups.slice(0, summarizeEnd).flat()
toKeep = groups.slice(min(specialTailStart ?? summarizeEnd, summarizeEnd)).flat()
```

然后调用 `vur(toSummarize, ...)`。如果成功，返回摘要及 `messagesToPreserve=toKeep`，不要求再总结保留尾部。

特殊尾部 `Pur:102887` 只有在 `tengu_clever_garden`（`xHs`，缺省 false）开启、至少三组、最后是合成 `No response requested.`、前一组是有效 assistant、该组估计不超过 **15,000 tokens**、且最后消息不是之前已保留消息等条件同时满足时，才多保留倒数第二组。因此“只保留一组”是默认，存在受旗标控制的例外。

## 5. 摘要请求也过长：如何计算下一步缩短多少

错误提取在 `chunk-wvsyb4fb.js:72055 h8e`：

```js
/prompt is too long[^0-9]*(\d+)\s*tokens?\s*>\s*(\d+)/i
tokenGap = actualTokens - limitTokens // 仅差值 >0 才返回
```

`Ien:72062` 还要求消息确实满足 `dme`（标记 API 错误，且文本以 `Prompt is too long` 开头）。解析不到真实用量就没有 tokenGap。

`Tur:102844`：

```js
if (tokenGap === undefined) return {mode: "gap_unparseable", step: 1}
return {mode: "gap_guided", step: edn(groupTokens, summarizeEnd, tokenGap)}
```

`edn:102837` 从当前摘要范围的**最后一组向前**累加，直到累计估计 token 数达到 gap；所得组数就是下一轮要额外移到原文保留区的 `step`。如果该步长会移走当前摘要范围里几乎所有组（`count >= summarizeEnd - 1`），改成 `max(1, floor(summarizeEnd / 2))`，避免立即跳空，继续阶梯探测。

`$ve:103150` 执行 `be += step`，然后重试。因此这是按实际超量引导的整组输入收缩，不是固定二分搜索，也不是每次都丢掉 20%。

人工数值推演：

```text
groups tokens = [1000, 4000, 3000, 2000, 1000]
初始 keep=1：总结 G0..G3，原文保留 G4
摘要接口返回 gap=2500
从 G3 累加 2000 不足，再加 G2=3000 => step=2
下一轮 keep=3：总结 G0..G1，原文保留 G2..G4
```

token 估计 `Og` 是本地估计，而 gap 来自服务错误；不能把这个样例理解成服务端一定接受第二轮。它还可能因为系统提示、工具定义、字节/token估计误差继续过长。

## 6. 最后兜底：总结全体可用内容，并必要时从头删整组

阶梯继续缩小，直到 `toSummarize` 没有 assistant 时（开场组特殊尝试除外）：

1. 禁止最后兜底则返回 `too_few_groups`（尚未尝试）或 `exhausted`（已经尝试）。
2. 允许则 `xur:102879` 找最新有效 assistant / 工具结果之后最后一个实际用户消息；将其及后面的消息留下，前面送摘要。找不到则全部送摘要、原文尾部为空。
3. 综合之前各次 gap、被移出摘要范围的 token 估计、初始 gap，推导兜底请求的差额。
4. `pXe` 检查摘要请求仍有实质内容；必要时先 `Fve` 从头删组后再检查。

`pXe:102857` 和 `tdn:102852` 的实质内容标准是：还有有效且非合成 `No response requested.` 的 assistant，或至少有实际用户消息且这些用户消息合计估计 **≥1,000 tokens**。

`Fve:107990` 才是“按 20% 裁剪”的函数：

```js
删除上一次自己加的 [earlier conversation truncated for compaction retry] 元消息
groups = a2(messages)
if (groups.length < 2) return null
if (gap 已知) 从最老组起累积 tokens，直到 >= gap
else dropCount = max(1, floor(groups.length * 0.2))
dropCount = min(dropCount, groups.length - 1) // 至少留下1组
remaining = groups.slice(dropCount).flat()
如果 remaining 以 assistant 开始，前面补一个 meta user 截断标记
```

如果媒体已剥离，`Fve` 的 token 估计也先对组应用 `jve`，避免按原来图片/文档体积误算。

`JZ=3` 在 `:107985`。兜底态再次过长时，`$ve:103123` 只有 `headTruncations<3` 才继续头部截断；初次进入兜底时若已按 gap 截过一次，计数从 1 开始。所以是**最多三次头部截断**，不是“所有压缩最多发三次 API”。

总结前若已经丢过头，生成的新摘要正文会明确提示最早历史没有被该摘要覆盖，完整 transcript 路径仍可用于查回（`QZ:102569`）。这是有损操作；原始 transcript 的存在不等于全部原始内容仍送给下一次模型请求。

## 7. 开场组特殊救援

`Jln:102860` 检查开场组是否足够有实质内容且大到值得先独立摘要：

```text
openingTokens - ceil(openingTokens/10)
    >= tokenGapAndPreservedOverhead + (20,000 + 5*5,000 + 25,000)
```

右侧固定加项等于 **70,000 tokens**，使用 `mXe=5,gXe=5000,hXe=25000`（`:107833`）。第二组首条若是 prompt-too-long assistant，也不走此救援。

满足时先只总结开场组，保留其余所有组。如果该次返回成功但没有 `<summary>` 标签，或一般错误，或媒体已剥离仍媒体错误，`Cur:102867` 会拒绝它，转入真正兜底头删路径。不能简单把任意纯文本都当这个特殊路径的可接受摘要。

## 8. 媒体错误：不是直接中止

`vur:102766` 将 `MSe` 分类为 `media_too_large`。

`$ve:103090` 第一次媒体过大：`Me=true; we--`，在**相同拆分**下重试。`jve:107874` 将 image/document 替换为 `[image]` / `[document]`，也处理工具结果数组与附件中的对应媒体。

再次媒体过大返回 `media_unstrippable`。`we--` 意味遥测“逻辑尝试数”不等于实际发出的请求数，不能拿 `attempts` 直接当模型调用次数。

## 9. 哪些失败会重试，哪些立即退出

`vur:102703` 只执行一次逻辑摘要回合，`maxTurns:1`、禁止工具、`skipTranscript:true`、`skipCacheWrite:true`。网络/API 层还可以有自己的重试，因此一次逻辑回合不一定等于一个 HTTP 请求。

| 摘要结果 | `$ve` 行为 |
|---|---|
| 正常非空摘要 | 成功，交给 `jRr` 重建上下文 |
| `prompt_too_long` | 改整组拆分；兜底态改头截断 |
| 首次 `media_too_large` | 媒体替换为占位，再试相同拆分 |
| 第二次媒体错误 | `media_unstrippable`，退出 |
| 用户取消 | `aborted`，退出 |
| 普通API错误、DLP、无assistant、空摘要、异常 | `error`，退出当前算法 |
| 共用 `compactionApiAttemptsLeft.count===0` | `exhausted`，退出 |

`vur` 还把 credits boundary 拒绝映射为 `prompt_too_long`，用 `Og(input)-vye` 构造差额，记录 `viaCreditsBoundary`；不能误以为所有 gap 都是服务端标准 context overflow。

## 10. 两类不同熔断器

### 连续失败熔断

`Ocn:109374`：失败计数 `previous+1`；`Dcn=3`。达到三次发 `tengu_auto_compact_circuit_breaker`。

`exr:109546` 判断：当没有 classifier overflow `xe`，且 `consecutiveFailures>=3`，返回 `failure_breaker_open`。这会跳过后续主动自动压缩；不能解释成整个 Claude 退出或所有响应式恢复永久关闭。状态是调用链传入的 compactTracking，日志虽写“this session”，具体持久化范围应以其调用者为准。

### 快速回填熔断

`Z4o:71380`：若上一次成功压缩后 `turnCounter<3` 又需压缩，连续快速回填计数加1；否则归零。`lTr:71383` 达 **3次**就 trip。`dbo:71387` 成功压缩后重置 turnCounter=0、consecutiveFailures=0，保留快速回填计数。

主循环 `pu:9800` 在工具回合继续往下走时 `turnCounter++`，不是终端用户发言次数。

主动入口 `exr:109570`、响应式入口 `pu:9145` 都检查这个保护；trip 后返回 `rapid_refill_breaker`，提示可能有超大文件/工具输出，建议分块读取或 `/clear`。

## 11. 主请求在成功压缩后如何防止无限再压缩

`pu:9141` 判断是否已做响应式恢复；通常一次已经做过，就通过 `hasAttempted` 拒绝再做。

成功且没有复用预计算摘要时，`pu:9305` 的条件允许**一次额外 deeper pass**：必须是 prompt-too-long、响应式支持、当前 deeper 状态 none、压缩后至少3组。下一次主请求仍过长且 transition 为 `reactive_compact_retry`，可以再进一次，并把状态从 available 改 spent。不是任意次数循环。

成功复用预计算摘要的 transition 是 `precomputed_compact_swap`，且 `hasAttemptedReactiveCompact=false`，不消耗现场响应式重算资格。所有分支仍受 abort、组数、快速回填和内部预算保护。

这与“摘要请求过长后内部 $ve 多次缩短重试”是两个层次，文档应分开画，否则容易把两次主请求恢复误写成只发两次摘要请求。

## 12. 预计算摘要为何不能无条件替换当前会话

`kvo:110642` 在阈值、idle、被暂扣413等入口消费/等待 ready 结果。pending 时会显示 compacting，`vvo:110604` 等待 settled 或 abort 后一次性消费；borrow 是另一条保持借出条目的路径。

`C4r`（`chunk-s7k1n636.js:2774`）至少检查：

1. 旧摘要覆盖终点 UUID 仍存在。
2. 被摘要覆盖的 row UUID 全都仍存在。
3. 应保留的旧消息没有消失。
4. 已覆盖历史之前没有插入该摘要没见过的非虚拟 assistant。
5. Hook 没有添加新 instructions、删边界或改写覆盖行前缀。
6. 摘要加保留尾部估算大小不会仍超阈值（`Ar:2816`）。

通过才返回 reuse，另带期间新增 `tail`；`CWn:103236` 将旧 `messagesToPreserve + 新tail` 一起重建。被拒则现场重算，或者 precomputedOnly 模式跳过。代码的已覆盖判断依赖 UUID 与行前缀，不是对每条消息全文做 cryptographic hash equality。

## 13. 旧 full compact 路径的重试规则

`QRr:108122` 调用 `hcn` 得摘要，若文本开头仍为 `Prompt is too long`，累加 `Gt`。`Gt<=3` 且API预算未耗尽才调 `ccn -> Fve`，更新 `forkContextMessages` 再发。因此常见上限是初次请求加3次头裁剪重试，受底层API预算/模型fallback变化约束。

`hcn:108652` 先尝试保留前缀的 `HR` cache-sharing；异常、无有效文本等可回退到独立摘要请求。回退会用 `jve` 剥离媒体，`stripNonEssential` 时还会 `ofr` 把工具输入/结果中的长字符串截到 **100字符** (`Vun=100,:107916`)，并移除thinking；它与响应式默认保留原文尾部是不同路径。
