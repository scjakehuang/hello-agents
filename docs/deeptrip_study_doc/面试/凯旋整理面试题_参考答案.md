## 一、技术基本功（40%）

### 1.1 存储

#### MySQL

**Q: 一条 SQL 从客户端到返回结果的完整执行路径是怎样的？**

```
客户端 → 连接器（认证、权限校验）→ 查询缓存（8.0 已移除）→ 分析器（词法分析、语法分析）
→ 优化器（选索引、Join 顺序、执行计划）→ 执行器（调用存储引擎接口）→ 存储引擎（InnoDB 读写数据页）
```

- **连接器：** 建立 TCP 连接，验证用户名密码，读取权限表
- **分析器：** 词法分析识别关键字和标识符，语法分析判断 SQL 是否合法
- **优化器：** 基于统计信息选择最优执行计划（RBO 规则优化 + CBO 成本优化），包括索引选择、Join 顺序、是否使用临时表
- **执行器：** 根据执行计划调用存储引擎 API，逐行扫描/索引查找，判断条件是否满足，返回结果集

**Q: InnoDB 的 B+ 树索引和 MyISAM 有什么本质区别？为什么 InnoDB 主键推荐自增？**

| 维度 | InnoDB | MyISAM |
|------|--------|--------|
| 索引数据存储 | 聚簇索引：主键索引的叶子节点存完整行数据 | 非聚簇索引：所有索引的叶子节点只存数据行地址 |
| 二级索引 | 叶子节点存主键值，回表查主键索引 | 叶子节点直接存行地址 |
| 事务 | 支持 | 不支持 |
| 行锁 | 支持 | 只支持表锁 |
| 崩溃恢复 | 有 redo log，crash-safe | 不支持 |

**自增主键好处：**
- B+ 树叶子节点是有序的，自增插入只需追加到最后页，不会导致页分裂和节点间数据搬移
- UUID 作为主键：每次插入可能插到中间位置 → 页分裂 → 碎片化 → 磁盘随机 IO 增加
- 二级索引存主键值，自增 int/bigint 比 UUID 小得多，二级索引更紧凑

**Q: 什么是覆盖索引？什么场景下索引会失效？**

**覆盖索引：** 查询涉及的列都在某个索引中，不需要回表查聚簇索引。Using index（Extra 字段）。

**失效场景（经典 7 种）：**
1. **最左前缀不满足：** 联合索引 `(a,b,c)`，`WHERE b=1` 不走索引
2. **索引列使用函数：** `WHERE DATE(create_time) = '2026-01-01'`
3. **隐式类型转换：** `WHERE phone = 13800138000`（phone 是 varchar）
4. **like 以 % 开头：** `WHERE name LIKE '%test'`
5. **不等于操作：** `!=` 或 `<>`（优化器可能选全表扫描）
6. **OR 条件中存在非索引列**
7. **优化器判断全表扫描更快**（数据量小或回表代价大）

**Q: 事务隔离级别有哪几种？InnoDB 怎么解决幻读？**

| 级别 | 问题 | InnoDB 实现 |
|------|------|------------|
| READ UNCOMMITTED | 脏读 | 无 |
| READ COMMITTED | 不可重复读 | 每次读取创建新 Read View |
| REPEATABLE READ（默认） | 幻读 | MVCC（快照读无幻读）+ Next-Key Lock（当前读防幻读） |
| SERIALIZABLE | 性能问题 | 读写都加锁 |

**MVCC 原理：**
- 每行有隐藏列：`trx_id`（事务ID）、`roll_pointer`（回滚指针指向上一个版本的 undo log）
- Read View：记录当前活跃事务列表，判断此版本是否可见
- 快照读（普通 SELECT）基于 MVCC，不产生幻读
- 当前读（SELECT ... FOR UPDATE / UPDATE / DELETE）对记录加 Next-Key Lock = 行锁 + Gap Lock，防止间隙插入新记录

**Q: 做过慢 SQL 优化吗？讲一个具体案例。**

典型方案：
1. **发现：** 慢查询日志 / APM 告警，`EXPLAIN` 看到 type=ALL，rows=50w
2. **分析：** `type` 从全表 → `const > eq_ref > ref > range > index > ALL`，`Extra` 关注 Using filesort/Using temporary
3. **优化手段：**
   - 加联合索引，使 WHERE + ORDER BY + GROUP BY 都在索引中
   - 改写为大表驱动小表，减少笛卡尔积
   - LIMIT 深分页改游标分页（`WHERE id > last_id LIMIT n`）
   - 读多写少场景，考虑冗余字段减少 Join
4. **验证：** 再次 EXPLAIN 确认 type=range/ref，线上观察 RT 从 3s → 50ms

**Q: 分库分表方案了解吗？**

- **时机：** 单表 > 500W-2000W 行，或单库 QPS > 2000，磁盘/连接数瓶颈
- **分库分表（水平拆分）：** 按分片键的 Hash 取模（`id % N`）或 Range
- **分片键选择原则：** 查询最多的维度，尽量避免跨分片
- **跨分片查询：**
  - 建立外部索引表（ES），通过 ES 先查 ID 再路由到对应分片
  - 广播查询所有分片后内存聚合（ShardingSphere 支持）
  - 基因法：ID 中包含分片信息（如 snowflake 的长 ID 含 worker id）
- **水平分表 vs 垂直分表：** 水平分表是行拆分，垂直分表是把不常用的大字段/列拆分

#### Redis

**Q: Redis 常用的数据结构有哪些？分别适合什么场景？**

| 结构 | 底层编码 | 场景 |
|------|---------|------|
| String | SDS | 缓存、计数器、分布式锁 |
| Hash | ziplist → hashtable | 对象存储（用户信息）、购物车 |
| List | quicklist | 消息队列（LPUSH+BRPOP）、时间线 |
| Set | intset → hashtable | 共同好友、标签、抽奖去重 |
| ZSet | ziplist → skiplist+dict | 排行榜、延迟队列（score=时间戳）、优先级队列 |
| Stream | rax tree | 持久化消息队列、消费者组 |
| GeoHash | ZSet | 附近的人 |
| Bitmap | String | 签到统计、布隆过滤器 |
| HyperLogLog | String | UV 去重统计（误差 0.81%） |

**Q: Redis 缓存穿透、击穿、雪崩分别是什么？怎么解决？**

| 问题 | 描述 | 方案 |
|------|------|------|
| 穿透 | 查一个不存在的数据，每次都穿透到 DB | 布隆过滤器提前拦截；或缓存空值（TTL 设短） |
| 击穿 | 热点 key 过期瞬间，大量请求打 DB | 互斥锁（先 SETNX 拿到锁的去查 DB 回种缓存）、逻辑过期 |
| 雪崩 | 大量 key 同时过期或 Redis 宕机 | 过期时间加随机抖动、限流降级、Redis 主从 + 哨兵高可用 |

**Q: Redis 的过期策略和内存淘汰机制？**

**过期策略（惰性 + 定期双管）：**
- **惰性删除：** key 被访问时检查，过期则删除。缺点：冷数据过期后不再访问就永远不删
- **定期删除：** 每 100ms 随机抽一批 key 检查，过期比例超 25% 则循环继续
- 组合效果：惰性删除兜底 CPU，定期删除兜底内存

**内存淘汰（8 种，maxmemory-policy）：**
- `noeviction`：不淘汰，写入报错（默认）
- `allkeys-lru / volatile-lru`：LRU
- `allkeys-lfu / volatile-lfu`：LFU（Redis 4.0）
- `allkeys-random / volatile-random`：随机
- `volatile-ttl`：淘汰最快过期的

生产推荐 `allkeys-lru` 或 `allkeys-lfu`（总有热冷之分时用 LFU）。

**Q: Redis 主从复制和哨兵模式的工作原理？Cluster 模式的数据分片机制？**

**主从复制：**
1. 从发送 PSYNC（replication id + offset）→ 主决定全量（RDB）还是部分（replication backlog 中仍有）
2. 全量：主 bgsave → 发 RDB 文件 + replication buffer 中积累的写命令

**哨兵模式：**
- 哨兵节点相互通信，对主节点做主观下线（SDOWN）→ 客观下线（ODOWN，多数哨兵同意）
- 哨兵 Leader 通过 Raft 选举选出，负责 failover：选新主（offset 最大、优先级最高）→ 通知其他从 replicate 新主

**Cluster：**
- Hash slot：16384 个 slot，`CRC16(key) % 16384` 映射到节点
- 每个节点负责部分 slot，节点间 gossip 协议交换信息
- 客户端可访问任意节点，MOVED 重定向或 ASK 热迁移中转
- 不支持多 key 跨 slot 操作（需用 hashtag `{userid}_key`）

**Q: 用 Redis 实现分布式锁要注意什么？**

```lua
-- 加锁（SET NX + 过期时间，原子操作）
SET lock_key random_value NX EX 30

-- 解锁（Lua 先验证 value 再删，防止误删别人的锁）
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

**关键点：**
- 必须原子操作（`SET NX EX` 一次完成，不要分步 `SETNX` 然后 `EXPIRE`）
- **random_value：** 解锁前必须对比，防止解锁别人持有中的锁（自己 GC 停顿超时后锁被他人获取）
- **RedLock 争议：** 多节点加锁解决单点问题，但 Martin Kleppmann 和 Redis 作者 antirez 有激烈讨论，实用中不建议过分迷信 RedLock
- Redisson 的看门狗（Watchdog）：自动续期，默认每 10s 续 30s

**Q: Redis Lua 脚本写过没有？**

写过，典型场景：
- 分布式锁的安全释放（上面的 unlock.lua）
- 库存扣减：Lua 脚本中检查库存 + 扣减 + 更新，一次原子操作
- 频率限制：INCR + EXPIRE + 阈值判断，原子化

**优势：** 原子化执行（单线程模型中无竞争）、减少网络往返。

#### MongoDB / ES（加分项）

**Q: MongoDB 和 MySQL 在设计理念上有什么本质不同？什么场景选 Mongo？**

| 维度 | MySQL | MongoDB |
|------|-------|---------|
| 数据模型 | 关系型，表 + 行，范式化 | 文档型，集合 + 文档，反范式化/嵌套 |
| Schema | 严格，DDL | 灵活，无 Schema 约束 |
| 事务 | 完整 ACID | 4.0+ 多文档事务（但性能不如单文档操作） |
| Join | 原生 SQL Join | 弱，用 `$lookup`，性能差 |
| 扩展 | 纵向为主，横向复杂 | 横向分片天然友好 |

**选 Mongo 的场景：**
- 数据格式多变（如不同活动类型字段不同）
- 高写入吞吐、低延迟读
- 1:N 关系且 N 很大但不会无限增长，可嵌套（如用户+地址）
- 快速原型、MVP 阶段

**Q: ES 的倒排索引原理是什么？和 MySQL 的全文检索有什么不同？**

**倒排索引：**
```
文档1: "Java 分布式 锁"
文档2: "Redis 分布式 锁 实现"
文档3: "Java Redis 缓存"

倒排索引：
Java  → [1, 3]
分布式 → [1, 2]
锁    → [1, 2]
Redis → [2, 3]
缓存  → [3]
实现  → [2]
```
- 分词 → 建立 term → docId 映射 → 查询时 term 交集 → 按 TF-IDF / BM25 打分排序

**与 MySQL 全文检索对比：**
- MySQL FULLTEXT 索引也是倒排索引，但分词能力弱（ngram），不支持中文分词
- ES 有专业分词器（IK Analyzer），天然分布式的搜索能力，支持高亮、聚合、模糊搜索等

### 1.2 网络

**Q: HTTP/1.1、HTTP/2、HTTP/3 的核心区别？**

| 维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|------|----------|--------|--------|
| 传输层 | TCP | TCP | QUIC（UDP-based） |
| 连接复用 | 无（6 conn/host） | 多路复用（1 conn，多个 stream） | 多路复用（无队头阻塞） |
| 队头阻塞 | 请求级 | TCP 流级别（仍存在） | 无 TCP 队头阻塞 |
| 头部压缩 | 无 | HPACK | QPACK |
| 服务端推送 | 无 | 支持 | 支持 |
| 连接迁移 | 不支持 | 不支持 | 支持（换网不断线） |

**多路复用：** HTTP/2 在一个 TCP 连接上并发多个 stream（帧间交错传输），但丢包时 TCP 重传会阻塞所有 stream。HTTP/3 用 QUIC，每条 stream 独立重传，彻底解决队头阻塞。

**Q: TCP 三次握手和四次挥手的过程？为什么是三次不是两次？**

**三次握手：**
```
客户端                          服务端
  |---SYN, seq=x---------------->|   1. 确认客户端发送能力
  |<--SYN+ACK, seq=y, ack=x+1---|   2. 确认服务端收发能力
  |---ACK, ack=y+1-------------->|   3. 确认客户端接收能力（防止旧连接请求误建连接）
```

**为什么不是两次：** 网络中存在老的 SYN 报文延迟到达，如果只有两次，服务端收到后直接建连接，但客户端早已放弃。三次握手时客户端在第三步才能拒绝这个过期的连接。

**四次挥手：**
```
客户端                          服务端
  |---FIN-------------------->|
  |<--ACK---------------------|  服务端可能还有数据要发
  |<--FIN---------------------|
  |---ACK-------------------->|  客户端等 2MSL
```

**TIME_WAIT 为什么等 2MSL：** 确保最后一个 ACK 能被服务端收到，如果丢失服务端会重发 FIN；同时让本次连接所有报文从网络中消失，不干扰下次同样端口的新连接。

**Q: TCP 的流量控制和拥塞控制是怎么做的？**

- **流量控制（端到端）：** 滑动窗口，接收方在 ACK 中告知 `rwnd`（接收窗口大小），发送方不得超过此值
- **拥塞控制（网络）：**
  - 慢启动：cwnd 指数增长到 ssthresh
  - 拥塞避免：超过 ssthresh 后线性增长
  - 快速重传：收到 3 个重复 ACK，不等超时就重传
  - 快速恢复：不降到 1 再慢启动，而是降到一半后直接从拥塞避免开始

**Q: WebSocket 和 SSE 有什么区别？分别适合什么场景？**

| 维度 | WebSocket | SSE |
|------|-----------|-----|
| 方向 | 双向 | 单向（服务端→客户端） |
| 协议 | ws://，独立协议升级 | HTTP（content-type: text/event-stream） |
| 断线重连 | 需自行实现 | 浏览器自带 EventSource 自动重连 |
| 穿透性 | 部分代理不支持 ws | 普通 HTTP，穿透无问题 |
| 复杂度 | 高（双向帧管理） | 低（只接收） |

- **WebSocket：** 实时协同编辑、游戏、即时通讯
- **SSE：** AI 对话流式输出、服务端状态推送、实时通知

**Q: HTTP 代理的原理？正向代理和反向代理的区别？**

- **正向代理：** 客户端 → 代理 → 服务器，代理代表客户端发请求（翻墙、内网出站），服务器不知道真实客户端
- **反向代理：** 客户端 → 代理 → 服务器，代理代表服务器收请求后转发（Nginx、API Gateway），客户端不知道真实服务器

**Q: 访问 HTTPS 网站从 DNS 到页面渲染的经历？**

```
DNS 解析（浏览器缓存→OS hosts→局域网DNS→根域名→顶级域→权威DNS，可能走 DoH）
→ TCP 三次握手
→ TLS 握手（ClientHello → ServerHello+证书 → 验证证书链 → 密钥交换 → Finished）
→ 发送 HTTP 请求
→ 服务端处理 → 返回响应
→ 浏览器解析 HTML → 构建 DOM 树 → 构建 CSSOM → 合成 Render Tree → 布局 → 绘制
→ 遇到外部资源（JS/CSS/IMG）→ 继续请求
→ JS 执行（阻塞解析，除非 async/defer）
```

**Q: 502 / 504 错误码的含义？**

- **502 Bad Gateway：** 网关/代理收到上游无效响应（上游服务挂了、返回格式不对）
- **504 Gateway Timeout：** 网关/代理等上游超时（上游处理太久）

### 1.3 操作系统 / Linux

**Q: 进程和线程的本质区别？协程呢？**

| 维度 | 进程 | 线程 | 协程 |
|------|------|------|------|
| 资源 | 独立内存空间、文件描述符 | 共享进程内存、独立栈 | 共享线程资源 |
| 切换开销 | 大（页表切换、TLB 刷新） | 中（内核态切换） | 小（用户态切换） |
| 调度者 | 操作系统 | 操作系统 | 用户代码/运行时 |
| 通信 | IPC（管道/共享内存/消息队列） | 共享内存 | 共享内存 |

**Java 虚拟线程（Project Loom）：** 在 JVM 层面将大量虚拟线程映射到少量 OS 线程（Carrier Thread），遇到阻塞（IO/网络）时自动 yield，让出 Carrier Thread 给其他虚拟线程。本质是 M:N 调度。

**Go 协程：** GMP 模型，goroutine → P（Processor）→ M（Machine/OS Thread），抢占式调度（基于信号的异步抢占），work-stealing 负载均衡。

**Q: 用户态和内核态的区别？系统调用的过程？**

- **用户态：** 受限指令集，不能直接访问硬件和内核内存
- **内核态：** 完整权限，可执行特权指令、访问所有内存
- **切换：** 系统调用 / 中断 / 异常 → 触发从 ring3 到 ring0 的切换

**系统调用过程：**
```
用户程序调用 read() → C 库封装 → 系统调用号存入 RAX，参数存入寄存器
→ syscall 指令（x86-64）→ CPU 切换到内核态
→ 内核在系统调用表中查找 RAX 对应的处理函数
→ 执行 → 结果返回 → 切换回用户态
```

**Q: BIO、NIO、IO 多路复用、AIO 的区别？**

| 模型 | 描述 | 代表 |
|------|------|------|
| BIO | 线程阻塞在内核，直到数据就绪+拷贝完成 | 传统 Socket |
| NIO | 轮询检查，就绪才读，非阻塞 | Java NIO（channel 设置为 non-blocking） |
| IO 多路复用 | 一个线程监听多个 fd，有就绪的再处理 | select/poll/epoll、kqueue |
| 信号驱动IO | 就绪时发 SIGIO 信号 | 用得少 |
| AIO | 发起读操作后立即返回，内核完成所有操作后回调通知 | 仅 Linux 支持少量场景 |

**select vs poll vs epoll：**
- select：fd_set 位图限制 1024，每次要从用户态全量拷贝到内核态，O(n) 遍历
- poll：pollfd 数组无大小限制，但仍是全量拷贝+遍历
- **epoll：** epoll_ctl 注册时只拷贝一次进红黑树，就绪事件放入双向链表，epoll_wait 只返回就绪的，O(1)。mmap 减少拷贝。边缘触发（ET）+ 非阻塞 socket 是高性能标配。

**Q: Java 应用内存持续上涨，怎么排查？**

```
top → 确认 Java 进程内存上升 → jstat -gc <pid> 1000 → 观察各区使用率+FGC
→ jmap -histo:live <pid> → 看哪些对象数量和大小异常
→ jmap -dump:live,format=b,file=heap.bin <pid> → MAT / JProfiler 分析
→ Dominator Tree 找最大的 Retained Heap → 追溯 GC Root 路径 → 定位内存泄漏点
→ 常见原因：ThreadLocal 没 remove、HashMap 无限增长、数据库查询返回过多行、静态集合忘记清理
```

**Q: CPU 使用率飙高，怎么排查？**

```
top -H -p <pid> → 找到 CPU 最高的线程 TID → printf "0x%x\n" <tid>
→ jstack <pid> | grep -A 20 <hex_tid> → 定位到代码行
→ 常见原因：死循环、正则回溯（灾难性回溯）、频繁 Full GC（STW 时 CPU 100%）、序列化大对象
```

**Q: Linux 常用命令考察**

```bash
# 端口占用
lsof -i :8080          # 哪个进程
ss -tlnp | grep 8080   # 更快的 netstat 替代

# 文件句柄数
cat /proc/<pid>/limits | grep "open files"  # 上限
ls -la /proc/<pid>/fd | wc -l               # 当前使用数
lsof -p <pid> | wc -l                        # 另一种查法

# 磁盘 IO
iostat -x 1           # %util、await、svctm
iotop                 # 哪个进程在大量 IO

# 日志
tail -f / grep "ERROR" / awk / sed
find . -name "*.log" -mtime +7 -exec rm {} \;  # 清理旧日志

# 统计
sort | uniq -c | sort -rn | head -20  # Top N 统计
```

## 二、业务理解与项目复杂度（35%）

### 2.1 项目复杂度

**Q: 讲一个你做过的**最复杂**的项目/需求。**

回答框架（STAR + Trade-off）：

**Situation：** 描述业务背景和项目目标
**Task：** 你的角色和职责
**Action：**
- 复杂在哪？（多维而不仅是"业务多"）：数据一致性要求高、多系统跨团队协作、高并发压力、并发竞态场景、异常路径多
- 做了哪些关键决策？（选型对比、trade-off 分析）
- 遇到的最大挑战？怎么解决？
**Result：** 量化效果（RT 降低 %、bug 数、QPS 承载、SLA 提升）

**加分要点：**
- 讲 "trade-off" 而非 "用了什么技术"：为什么选方案 A 不选 B，放弃了什么，换来什么
- 讲 "坑"：只有真做过才会踩坑，也才会记得
- 对指标敏感：上线后盯着什么数据判断成败

**Q: 一个需求从接收到上线，你的完整流程是怎样的？**

```
需求理解 → 技术方案 → 编码实施 → 测试 → 上线 → 验证

1. 需求理解：
   - 找 PM/业务方澄清：输入什么、输出什么、什么条件触发、失败了怎么办
   - 拉上 QA 一起过 AC，对齐边界场景的期望行为
   - 反问：如果没有这个功能，用户现在怎么做的？痛点是什么？

2. 技术方案（至少覆盖）：
   - 正常流程：happy path
   - 异常流程：下游超时/返回错误/数据异常/幂等等
   - 边界条件：空值、极端数量、并发竞态
   - 性能：QPS 预估、RT 目标、缓存策略
   - 安全：认证鉴权、参数校验、SQL 注入、敏感信息脱敏
   - 可观测性：关键日志、指标、告警

3. 编码 → 单元测试 → 本地验证 → Code Review → 提测

4. 上线：
   - 灰度策略（% 用户 / 白名单）
   - 回滚方案
   - 监控面板就位

5. 验证：1h/24h/7d 看数据：RT、错误率、业务转化率、用户反馈
```

**Q: 有没有遇到过需求频繁变更的情况？你怎么处理？**

核心原则：**对变化隔离，对不变提取。**

- 主动需求澄清阶段就挖出 PM 没写的"隐藏变化点"
- 方案设计时分清变与不变：变的部分封装成策略/配置，不变的部分抽象成稳定接口
- 避免过度设计：不确定是否变的东西先不抽象，等第二次变化出现时再重构
- 需求变更过大时主动沟通排期影响，不要默默扛

### 2.2 业务价值理解

**Q: 你如何理解"技术服务于业务"？**

技术选择不以"新技术/流行/简历加分"为判据，以能否解决业务问题为第一判据。比如，一个低并发内部系统用 Redis 就够，不需要上 Flink 做流式处理。

**Q: 当技术方案和业务交付时间冲突时，你怎么权衡？**

- 核心是"范围谈判"而非"牺牲质量"：先做 MVP 范围，把非核心部分留二期
- 不能牺牲的底线：数据安全、资金准确性、生产数据不可逆操作
- 可牺牲的：管理后台操作便捷性、非核心报表、性能优化（满足目标即可）

**Q: 你怎么看待"技术债"？**

- 从商业角度衡量：利率是什么（每次加功能多花多少时间）、本金多少（还清要多久）
- 高利率小本金 → 立刻还（如：核心路径的 if-else 面条代码）
- 低利率大本金 → 分期还、做新功能时顺带改
- 零利率 → 放着别动

### 2.3 多系统协作（DeepTrip 场景）

**Q: 设计对话全链路追踪系统？**

**需要记录的信息：**

```json
{
  "traceId": "全局唯一",
  "spanId": "每层自己的 span",
  "parentSpanId": "上游 span",
  "service": "dt-main | agent-b101 | dataset-service",
  "timestamp": "开始时间",
  "duration": "耗时",
  "input": {
    "user_message": "...",
    "context": {"session_id": "...", "channel": "H5"}
  },
  "output": {
    "reply": "...",
    "tokens": 150,
    "tool_calls": ["query_flight", "search_hotel"]
  },
  "status": "success | error",
  "error": {"message": "...", "stack": "..."},
  "metadata": {"model": "claude-sonnet-4-6", "env": "production"}
}
```

**存储方案：**
- 链路宽度在请求入口生成 traceId 注入请求头（透传）
- 各层 span 异步写 ES / ClickHouse（从响应中提取 traceId）
- 用 traceId 聚合展示完整调用链路
- 关键指标：每层耗时占比、工具调用成功率、LLM Token 用量

**Q: SSE 流式接口断了，怎么定位？**

```
客户端断连 → Nginx 上看到 499（客户端主动断开）还是 upstream 超时返回 504
如果 Nginx error_log 看到 "upstream timed out" → 检查 dt-main 的 /chat/stream 接口
dt-main 日志看 → 是 SSE 请求转发的 /agent/chat 超时了？
  是 → agent-b101 日志看 → LLM 调用超时还是工具调用卡住？
  不是 → dt-main Filter 链中间环节（鉴权、参数校验、Redis 状态读取）卡住？
最后定位到具体哪一层哪个环节。
```

**Q: 260+ 接口核心链路流量回放验证怎么设计？**

```
录制：Nginx 层按比例录制请求（request + response），写入 Kafka → S3
      或基于网关层的 access log 提取关键接口的请求体
回放：从 S3 读 → 脱敏（手机号/身份证/Token 替换）→ 发到 Gray / Staging 环境
     对比新旧 response（忽略时间戳、UUID 等动态字段）
     差别写入报告 → 人工判断是预期变化还是回归 bug
难点：下游依赖的数据状态是否一致（同一请求在不同时间执行，下游数据可能已变）
解决：只对比接口结构/字段完整性，不做字段值精确对比
```

## 三、AI 理解与应用（25%）

### 3.1 AI 基础理解

**Q: 你怎么理解 LLM 的工作原理？Token、Context Window、Temperature 这些概念？**

- **Token：** LLM 不是按字而是按 token 计费和计算。1 token ≈ 英文 0.75 词，中文 ≈ 1-2 字。输入+输出都消耗 token。
- **Context Window：** 模型能"看到"的最大上下文长度（Claude 200K，GPT-4 128K）。超出的内容会被截断或压缩。
- **Temperature（0-1）：** 控制输出随机性。0 = 确定性（分类/抽取场景），1 = 高创造性（写作/头脑风暴）。
- **核心原理（简述）：** 自回归 Transformer → 基于上文 token 序列预测下一个 token 的概率分布 → 采样 → 重复。整个过程是概率性的，没有"知识"，只有"模式匹配"。

**Q: RAG 是什么？解决什么问题？**

**RAG = Retrieval Augmented Generation（检索增强生成）**

解决 LLM 的三个核心问题：
1. **知识截止：** 训练数据有时效性，RAG 提供实时知识
2. **幻觉：** 用检索到的文档约束回答，减少凭空编造
3. **私有知识：** 企业内部文档无法放入训练数据

**流程：** 用户问题 → Embedding → 向量库检索 top-k 相关文档 → 拼入 prompt → LLM 基于这些文档回答。

**Q: AI Agent 和传统"调用 API"有什么本质不同？**

| 传统 API 调用 | AI Agent |
|-------------|----------|
| 固定输入输出 | 自主推理+决策 |
| 流程代码写死 | LLM 根据目标动态选工具 |
| 无记忆（除非代码处理） | 短期记忆（上下文）+ 长期记忆（外部存储） |
| 失败 → 抛异常 | 失败 → 反思 → 换方案重试 |

**Agent 核心四能力：**
1. **规划（Planning）：** 大任务拆成小步骤，多步推理（CoT/ToT）
2. **工具调用（Tool Use）：** 选择合适的 API/工具执行
3. **记忆（Memory）：** 处理过程中的中间状态和结果
4. **反思（Reflection）：** 检查结果是否正确，不对则纠偏

**Q: Function Calling / Tool Use 的机制？如果让你设计一个框架你怎么做？**

工作流程：
1. 定义工具 schema（函数名、描述、参数 json schema）→ 在 system prompt 中注入
2. 用户提出请求 → LLM 推理后输出想调用的函数名 + 参数（不是文本，是结构化输出）
3. 收到函数名 + 参数 → 实际执行 API 调用 → 获取结果
4. 把工具执行结果加入对话上下文 → LLM 基于结果生成最终回复

**框架设计要点：**
```
Tool Registry → 注册/发现工具
Tool Executor → 执行工具调用，捕获错误
Output Parser → 解析 LLM 的工具调用输出
Result Injector → 将工具结果插入对话上下文
Guardrail → 校验：参数合规？权限足够？即使 LLM 说"执行 X"，也要代码侧再判断一次
```

**Q: 为什么选择 LangChain？**

选择 LangChain 不是因为"它流行"，而是它在特定场景有价值：
- 需要快速原型验证，LangChain 提供开箱即用的 RAG chain、Agent executor
- 需要对接多个 LLM 提供商时，LangChain 的 ChatModel 抽象省很多适配代码

**不选择 LangChain 的原因（生产环境）：**
- 抽象层太厚，出了问题很难定位到具体哪步
- Agent Executor 的隐式 prompt 和逻辑，不是所有场景都适用
- 版本迭代太快，API breaking changes 多
- 对性能敏感的大流量场景不友好

**正确用法：** 薄层使用：只用 LangChain 的 ChatModel 封装 + Message schema，编排逻辑自己写。

### 3.2 AI 工具使用

**Q: 你日常开发中用 AI 工具吗？**

- 用 Claude Code / Cursor 做主力开发辅助
- 主要用途：代码生成（70%）、bug 排查（15%）、文档和注释（10%）、新框架学习（5%）
- 效率提升：日常编码中 AI 可完成约 40-50% 的工作量，尤其擅长重复性代码和改造迁移
- 局限性：
  - 能写好"有明确上下文"的代码，但"跨文件设计决策"不行
  - 会犯错（generate 看起来对但逻辑有问题的代码），需要 review
  - 对业务领域知识盲区：不画图不写设计文档讲不清的逻辑，AI 也写不对代码

**Q: 你觉得一个好的 Prompt 应该怎么写？**

方法论（CLEAR + 迭代）：

1. **Context（背景）：** 这个功能是干什么的，项目结构是怎样的
2. **Instructions（指令）：** 明确要求做什么，格式是什么
3. **Examples（示例）：** 展示期望的输入输出（few-shot）
4. **Constraints（约束）：** 不能用什么，要注意什么，输出限制
5. **Evaluation（检验）：** 告诉它怎么自查（"确认你的代码中没有 N+1 查询"）

迭代原则：不是一次写好，而是写 → 看输出 → 找偏差 → 改 prompt → 再看。

**Q: AI Coding Agent 和 AI Editor 的区别？**

- **AI Editor（Cursor/Copilot）：** 补全+局部编辑，人主导（ctrl+z 回退到人），你可以理解每一步
- **AI Coding Agent（Claude Code/Devin）：** 自主执行多步骤任务（读文件→理解→写代码→跑测试→修复→提交），你不一定理解每一步。好处是能处理大范围改动，坏处是出了问题需要看 diff。

### 3.3 AI 在业务中的落地

**Q: 你对 agent 这个词的理解？**

Agent 是一个具备自主性的智能程序——给定目标后，它能自主感知环境状态、推理下一步动作、调用工具执行、评估结果并迭代调整，直到目标达成。

区别于传统自动化脚本的关键是"自主性"：脚本只能执行预设步骤，Agent 可以在没见过的情况下做出有意义的决策。

**Q: 入职后如何引入 AI 能力？**

切入顺序（从低风险到高风险）：
1. **内部工具：** 运营后台的智能搜索、工单自动分类、知识库问答（错了不会影响终端用户）
2. **辅助决策：** CK 分析报告自动生成、代码review 辅助检查
3. **用户侧：** 智能客服对话、旅行行程智能规划
4. **自动化操作：** 自动配置、自动上线（需要更高成熟度）

**Q: AI 友好的代码/架构长什么样？**

- 工具调用接口有清晰的 schema 描述（自然语言 + JSON Schema），LLM 能直接理解
- 接口原子化：一个功能一个接口，而不是一个大接口做所有事（颗粒度对 LLM 友好）
- 响应中有足够上下文（不只是 `{code: 0, data: {}}`，错误信息要能直接喂回给用户）
- 幂等设计：Agent 可能重复调用同一个工具

**Q: 3 年后的后端工程师应该具备什么能力？**

- 不是"AI 替代你写代码"，而是"AI 帮你写代码，你把控方向和质量"
- 核心能力变化：从"写代码快"→ "做正确决策快"（trade-off 分析能力更重要）
- 新必备能力：Prompt 设计、Agent 编排、AI 输出验证、从 AI 生成代码中识别 bug 的能力
- 软技能更重要：和 PM 对齐价值、推动跨团队合作、说服别人采纳方案——这些 AI 暂时替代不了

**Q: 团队提效的具体做法？**

- 推进 AI Code Review 工具减少 Reviewer 负担
- 写 SOP + 自动化脚本减少重复操作（如之前提到的迁移 SOP 5天→2天）
- 共享配置 SDK 解耦四团队协作成本
- 引入 AI 辅助生成测试集提升覆盖率

## 四、开放 / 综合题

**Q: 你会投入时间学习或研究什么技术？**

工作相关优先：当前业务需要的技术栈深入（如存储原理、分布式系统一致性协议），其次是 AI 趋势跟踪（新模型能力、Agent 框架演进）。

**Q: 在团队中推广过某个技术或工具的经历？**

用"试点→数据说话→开源/文档→降低迁移成本"四步法。关键是不要靠"我觉得好"去推广，而是找一个明确痛点，证明新方案能解决它，并且提供迁移指南让别人成本最低。

**Q: 和同事在技术方案上有分歧的经历？**

正常流程：
1. 理解对方真正在意什么（性能/可维护性/工期/风险？）
2. 客观对比两个方案的优劣，不做人身攻击
3. 如果僵持不下：找 TL/架构师仲裁，尊重决定
4. 即使自己的方案被否了，也要全力执行团队决定的方案

**Q: 对加班怎么看？对远程办公怎么看？**

- **加班：** 不排斥因项目需要短期加班（上线、紧急 bug），但抵制"无效加班"（等 PM、等 QA、开没结论的会）。如果长时间加班是常态 → 流程或规划问题而非人力问题。
- **远程办公：** 完全接受混合办公模式。异步沟通能力（写清楚文档/设计稿/AC）比同步开会更重要。
