#### 1. 并发编程：CompletableFuture 与线程池

**题目：** 你在 SEND 项目中后端 fan-out 生成 2ⁿ 种报价组合，假设每个报价需要调用 3 个独立的下游服务。请用 Java 写出并发调用方案，并说明线程池参数如何配置。

**参考答案：**

```java
public class QuoteService {
    private final ExecutorService executor = new ThreadPoolExecutor(
        8, 16, 60L, TimeUnit.SECONDS,
        new LinkedBlockingQueue<>(200),
        new ThreadPoolExecutor.CallerRunsPolicy()
    );

    public List<Quote> generateQuotes(List<ServiceConfig> configs) {
        return configs.parallelStream()
            .flatMap(config -> {
                // 每个报价组合并发调用 3 个下游服务
                CompletableFuture<Price> priceFuture =
                    CompletableFuture.supplyAsync(() -> fetchPrice(config), executor);
                CompletableFuture<Tax> taxFuture =
                    CompletableFuture.supplyAsync(() -> fetchTax(config), executor);
                CompletableFuture<Pickup> pickupFuture =
                    CompletableFuture.supplyAsync(() -> fetchPickup(config), executor);

                return CompletableFuture.allOf(priceFuture, taxFuture, pickupFuture)
                    .thenApply(v -> assembleQuote(
                        priceFuture.join(), taxFuture.join(), pickupFuture.join()))
                    .join();
            })
            .collect(Collectors.toList());
    }
}
```

**关键点：**
- **核心线程数 8、最大 16：** CPU 密集 + I/O 密集混合场景的通用配置
- **有界队列 200：** 防止无界队列导致 OOM
- **CallerRunsPolicy：** 温和降级，不丢任务，让调用线程执行
- **并行流 `parallelStream()`：** fork-join 池适用于 CPU 密集，但这里外层配置数量通常不大（假设 10-20 个）

**追问：** 如果下游某个服务 P99 延迟是 2s，如何设置超时？

```java
CompletableFuture.supplyAsync(...)
    .orTimeout(3, TimeUnit.SECONDS)
    .exceptionally(ex -> getDefaultPrice(config));
```

#### 2. 微服务设计：降级与容错

**题目：** 你在 nPCP 项目中设计了 4 层降级缓存（内存 → AppConfig → 磁盘 → 包内置），请画出类设计并说明每一层的触发条件。

**参考答案：**

```java
public class ConfigClient {
    private final Cache<String, Config> memoryCache;   // L1: Caffeine, TTL 30min
    private final AppConfigClient appConfig;            // L2: AWS AppConfig
    private final FileConfigStore diskStore;            // L3: 本地磁盘
    private final Map<String, Config> bundledDefaults;  // L4: jar内置

    public Config get(String key) {
        // L1: 内存缓存
        Config cfg = memoryCache.getIfPresent(key);
        if (cfg != null) return cfg;

        try {
            // L2: AppConfig
            cfg = appConfig.getConfig(key);
            memoryCache.put(key, cfg);
            diskStore.writeAsync(key, cfg); // 异步写盘
            return cfg;
        } catch (AppConfigException e) {
            log.warn("AppConfig unavailable, trying disk", e);
        }

        // L3: 磁盘
        cfg = diskStore.read(key);
        if (cfg != null) {
            memoryCache.put(key, cfg);
            return cfg;
        }

        // L4: 包内置默认值
        log.warn("Using bundled default for key={}", key);
        return bundledDefaults.getOrDefault(key, Config.EMPTY);
    }
}
```

**关键设计决策：**
- L1→L2 降级：网络故障或 AppConfig 超时（P99 < 20ms 满足时不会触发）
- L2→L3 降级：AppConfig 不可用（需报警）
- L3→L4 降级：磁盘损坏或首次启动无缓存文件
- L1 的 TTL 用 30min，平衡一致性与可用性
- 异步写盘不阻塞主路径

#### 3. JVM 与性能：GC 与内存模型

**题目：** 你的 SEND 系统承接了 2.17 亿次请求，在高并发下如何排查 Full GC 频繁的问题？Java volatile 关键字在配置热更新场景中如何保证可见性？

**参考答案：**

**GC 排查步骤：**
1. `jstat -gc <pid> 1000` 观察 GC 频率和各代使用率
2. `jmap -histo <pid>` 找出大对象，排查内存泄漏
3. 确认是否创建了过多短命大对象（如未设置大小的 ByteArrayOutputStream）导致频繁 Young GC 晋升并触发 Full GC
4. 调优方向：增大 Young 区、控制大对象直接进老年代阈值（`-XX:PretenureSizeThreshold`）

**volatile 在配置热更新场景：**

```java
public class AppConfigHolder {
    private volatile Config currentConfig; // volatile 保证多线程可见性

    public void refresh() {
        Config newConfig = fetchFromRemote();
        // volatile 写：立即刷入主内存，其他线程下次读时立即可见
        this.currentConfig = newConfig;
    }

    public Config get() {
        // volatile 读：从主内存读取，不用工作内存缓存
        return currentConfig;
    }
}
```

**关键点：** volatile 只保证可见性和禁止指令重排，不保证原子性。这里 Config 对象的引用赋值是原子操作，所以 volatile 足够。如果需要 read-modify-write（如计数器），需用 AtomicInteger 或 synchronized。

#### 4. 设计模式：状态模式 vs 状态机

**题目：** 你在 Azwraith AI Agent 中使用状态机约束 LLM 行为。请用 Java 实现一个简化版的入驻状态机，包含「知识审核→IAM配置→API Key部署→完成」四个阶段，每阶段仅暴露合法的操作。

**参考答案：**

```java
// 状态枚举
enum OnboardingStage {
    KNOWLEDGE_AUDIT, IAM_CONFIG, API_KEY_DEPLOY, COMPLETED
}

// 状态机
public class OnboardingStateMachine {
    private final DynamoDBTable ddb;
    private static final Map<OnboardingStage, Set<Activity>> STAGE_ACTIVITIES = Map.of(
        KNOWLEDGE_AUDIT, Set.of(Activity.KENDRA_QUERY, Activity.VALIDATE_BUSINESS_INFO),
        IAM_CONFIG, Set.of(Activity.VALIDATE_ROLE_ARN, Activity.VALIDATE_ROLE_POLICY),
        API_KEY_DEPLOY, Set.of(Activity.PUBLISH_CR, Activity.VERIFY_API_KEY),
        COMPLETED, Set.of()
    );

    public Set<Activity> getAllowedActivities(String simId) {
        OnboardingStage stage = ddb.getStage(simId);
        return STAGE_ACTIVITIES.getOrDefault(stage, Set.of());
    }

    // LLM 输出结构化意图后，校验是否允许执行
    public void validateAndExecute(String simId, Activity requested) {
        Set<Activity> allowed = getAllowedActivities(simId);
        if (!allowed.contains(requested)) {
            throw new IllegalStageTransitionException(
                "Activity " + requested + " not allowed in current stage");
        }
        executeActivity(simId, requested);
    }

    public void advanceToNextStage(String simId) {
        OnboardingStage current = ddb.getStage(simId);
        OnboardingStage next = switch (current) {
            case KNOWLEDGE_AUDIT -> IAM_CONFIG;
            case IAM_CONFIG -> API_KEY_DEPLOY;
            case API_KEY_DEPLOY -> COMPLETED;
            case COMPLETED -> COMPLETED;
        };
        ddb.setStage(simId, next);
    }
}
```

**设计要点：**
- 单向不可逆：状态只能向前，防止 LLM 乱序操作
- 最小权限：每阶段仅暴露合法的 Activity 集合
- DDB 持久化：状态机数据存 DynamoDB，Lambda 无状态 + DDB 持久化保证可靠性

#### 5. Lambda 架构：限速与幂等

**题目：** 你在 OSS 项目中设计了 0.3 TPS × 10 Lambda Poller 的限速方案。请设计一个通用的分布式限速器，并说明 Lambda 场景下如何保证幂等。

**参考答案：**

**分布式限速器：**

```java
public class DistributedRateLimiter {
    private final DynamoDBTable ddb;
    private final int pollerIndex;
    private final int totalPollers;

    // 每个 Poller 的本地令牌桶
    private final RateLimiter localLimiter = RateLimiter.create(0.3);

    public boolean tryAcquire() {
        // 本地限速（粗粒度）
        if (!localLimiter.tryAcquire()) return false;

        // DDB 条件写入（细粒度，全局一致性）
        String minuteKey = LocalDateTime.now().format(DateTimeFormatter.ofPattern("yyyyMMddHHmm"));
        try {
            ddb.updateWithCondition(
                "rateLimitCounter", minuteKey,
                "ADD counter :inc", Map.of(":inc", 1),
                "counter < :max", Map.of(":max", 60) // 全局 1 TPS → 60/min
            );
            return true;
        } catch (ConditionalCheckFailedException e) {
            return false; // 达到全局上限
        }
    }
}
```

**Lambda 幂等保证：**

```java
public void handleEvent(SQSEvent event) {
    for (SQSEvent.SQSMessage msg : event.getRecords()) {
        String idempotencyKey = msg.getMessageId(); // 或业务唯一键
        try {
            ddb.putWithCondition(
                "idempotency", idempotencyKey,
                "attribute_not_exists(idempotencyKey)"
            );
            processMessage(msg);
            ddb.updateStatus(idempotencyKey, "COMPLETED");
        } catch (ConditionalCheckFailedException e) {
            // 已处理过，跳过
            log.info("Duplicate message skipped: {}", idempotencyKey);
        }
    }
}
```

#### 7. Agent 编排与状态机

**题目：** 你设计的固定单向状态机约束 AI 行为，这种方式与 ReAct / Function Calling 有什么本质区别？什么场景下状态机更合适？

**参考答案：**

| 维度 | 固定状态机 | ReAct / Tool Calling |
|------|----------|----------------------|
| 控制权 | 流程由代码控制，LLM 只做推理 | LLM 自主决定下一步操作 |
| 安全性 | 极高，不会走出预期流程 | 需额外 guardrail，可能误调用 |
| 灵活性 | 低，新增步骤需改代码 | 高，LLM 可自主排列组合 |
| 适用场景 | 流程固定、安全敏感的 BPM | 开放式、探索式任务 |
| LLM 角色 | 意图识别 + 内容生成 | 推理 + 决策 + 执行 |

**状态机合适的场景（如 Azwraith）：**
- 业务流程有法律/合规约束（入驻审批 → 配置 → 部署顺序不可乱）
- 每个阶段的操作集合是有限的、可枚举的
- 错误成本高（IAM 错误配置可能导致安全漏洞）

**ReAct 合适的场景（如旅行助手）：**
- 用户意图多样，无法穷举
- 工具调用顺序不确定（先查机票还是先查酒店不固定）
- 需要多步推理的开放式问答

当前阶段允许的操作：{allowed_activities}

用户消息：{user_message}

只输出 JSON，不要包含任何其他文字。不要使用 markdown 代码块。
```

**不稳定输出及修复：**

| 问题 | 原因 | 修复 |
|------|------|------|
| LLM 输出 ````json { ... } ```` 包裹 | 模型倾向于 markdown 格式化 | Prompt 末尾加"不要使用 markdown 代码块"，或 parser 中 strip ````标记 |
| intent 输出不在枚举值中 | 约束不够强 | 用工具调用（tool_use/function calling）而非文本生成 |
| JSON 中有尾随逗号 | 部分模型问题 | 单独再加一个 JSON 修复/重试步骤（解析失败时重试） |
| 空输出或截断 | max_tokens 不够 | 设足够大 + 检查 `finish_reason` 是否为 `length` |

#### 14. 开放讨论：LLM 在业务流程中的定位

**题目：** 你认为 LLM 在企业业务流程中应该扮演什么角色？是「决策者」还是「翻译官」？请结合 Azwraith 的设计哲学回答。

**参考答案（基于候选人项目风格）：**

**LLM 应该是「翻译官 + 文书」，不是「决策者」。**

Azwraith 的设计明确体现了这一点：
- **状态流转**由代码状态机控制（非 LLM 决策）
- **操作集合**由每阶段预定义的白名单控制（非 LLM 决策）
- **安全关键操作**有二次确认 + 审计日志（非 LLM 自行判断）

LLM 的角色是：
1. **自然语言 → 结构化意图：** 理解货代"我想加个德国仓"→ `{intent: EXECUTE_ACTIVITY, activity: ADD_WAREHOUSE, parameters: {country: "DE"}}`
2. **结构化结果 → 自然语言回复：** API 返回 `{"error": "role_arn_invalid"}` → "您的 IAM Role ARN 格式不正确，请确认格式为 `arn:aws:iam::...`"
3. **知识检索结果 → 易懂回答：** Kendra 返回 3 段文档 → 精炼成货代能理解的答案

**为什么不让 LLM 做决策：**
- 状态机的边界是业务逻辑（法律/合规/安全），不能让概率模型决定
- LLM 可能被 prompt injection 诱导跳过关键步骤
- 审计追溯需要确定性行为，`if stage == IAM_CONFIG and activity == PUBLISH_CR: deny` 比 prompt 约束可靠得多
