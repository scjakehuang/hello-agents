## 一、Multi-Agent 架构设计（猫超 AI 导购员 — 核心项目）

### Q1：DAG 分层架构的工程细节

简历提到基于 xLangChain+TPP 图引擎设计了 5 层分层架构，各模块通过注解声明依赖关系，框架自动推导 DAG 拓扑与并行度。

1. 「注解声明依赖关系，框架自动推导 DAG 拓扑」——这个注解你们是怎么定义的？具体包含哪些元信息？推导拓扑的核心算法是什么？
2. 5 个意图子 Agent 并行执行——它们的并行是无条件的吗？还是某些 Agent 之间有数据依赖？如果有依赖怎么处理？
3. 执行路由层是怎么根据意图类型分发到不同处理链路的？用了什么路由策略？
4. 如果某个子 Agent 执行超时或失败，DAG 引擎怎么处理？是整体失败还是局部降级？

> **考察意图：** "注解驱动 + 自动推导 DAG"是自己实现的还是直接用框架内置能力。Q4 的异常处理是区分 demo 和生产的核心问题。

### Q2：单体拆 Multi-Agent 的决策过程

你说从单体拆成 5 个并行 Agent，解决了 Prompt 冗长和输出慢的问题：

1. 拆分的决策依据是什么？尝试过其他拆分粒度吗（比如 3 个或 7 个）？实验数据是怎样的？
2. 拆分后，单体 Prompt 大约多少 tokens、多 Agent 模式分别是多少？延迟从多少降到多少？
3. 拆分有没有引入新的问题？比如子 Agent 之间信息传递的损失？怎么解决的？
4. 你怎么判断某个 case 适合用单体还是多 Agent？AB 实验的决策指标是什么？

> **考察意图：** 拆分不是越细越好，问边界和 trade-off 能看出是否真的思考过架构决策，而非为了简历效果堆砌概念。

## 二、模型微调经验（猫超 AI 导购员 — 模型微调）

### Q3：SFT + DPO 两阶段微调细节

你基于 Qwen3-30B-A3B 做了 SFT+DPO 微调，Query 准确率 57% → 76.6%：

1. 为什么选 Qwen3-30B-A3B（MoE 模型）而不是其他模型？考虑过哪些替代方案？
2. SFT 阶段的训练数据怎么构造的？数据量多大？数据分布是怎样的（比如商品类目覆盖度）？
3. DPO 阶段的正负样本对怎么生成的？"正样本"的定义是什么——是人工标注还是规则生成？负样本是同 Query 的错误改写还是不同 Query 的改写？
4. 微调用了什么框架（LLaMA-Factory、Axolotl、自研）？用了多少 GPU、训练了多久？有没有做量化？
5. 76.6% 这个准确率在业务上的甜区是什么状态？你觉得继续优化的瓶颈在哪里？

> **考察意图：** 模型微调是简历含金量最高的点之一。从模型选型、数据构造、训练框架到效果分析，每个环节都能区分"真做过"和"参与过"。Q5 问天花板判断他的技术判断力。

### Q4：自动化评测闭环

你构建了"LLM 多模型投票 + 搜索工具验证"的自动化离线评估链路：

1. 多模型投票用了哪些模型？投票机制是什么（多数票、加权票、全票通过）？
2. "搜索工具验证"具体怎么做的——是拿改写后的 Query 实际调用搜索引擎看召回结果，还是有其他验证方式？
3. 这个评测链路本身怎么检验它的可靠性？有没有和人工标注做过对比？
4. 训练数据自动标注——标注质量怎么保证？有没有做人工抽检？发现过标注噪声吗？
5. 评测集是怎么维护的？有没有做定期更新或防止过拟合的措施？

> **考察意图：** 评测是 ML 工程中最难且最容易被忽视的环节。问评测链路本身的可靠性、标注质量控制，能看出他对 ML 工程全流程的理解深度。

## 三、后端工程能力（巡检系统 + 渠道化表达）

### Q5：Pipeline 与扩展点设计

你在巡检系统和渠道化表达两个项目中都用到了 Pipeline 架构：

1. 两个项目的 Pipeline 设计有什么异同？是复用了同一套框架还是各自实现？
2. 巡检系统的「原子动作四件套」——Param/Wrapper/Context/LiveAction 四层分别解决什么问题？为什么是这四层而不是三层或五层？
3. 渠道化的 10 个 Handler 节点，节点之间的数据是怎么传递的？用一个共享 Context 还是节点间显式传递？
4. 如果某个 Handler 需要跳过、或者新增一个 Handler 在中间插入，是怎么做到的？
5. 责任链和策略模式你分别用在什么场景？两个模式的边界在哪？

> **考察意图：** 两个项目都有 Pipeline，问异同能看出是碰巧用了同一模式还是对架构模式有体系化认知。Q2 的"为什么四层"测试设计直觉。Q4 测试扩展性的实际体验。

### Q6：渠道化表达的配置化设计

你设计了 Diamond 四层配置体系实现新增因子零代码接入：

1. 四层配置的每一层具体长什么样？能给一个配置示例吗（JSON/YAML 均可，口述即可）？
2. "零代码或低代码"——什么情况零代码、什么情况需要低代码？边界在哪？
3. 配置驱动的系统，配置错误怎么防范？有没有做配置校验或灰度？
4. 这个配置体系和业界的"配置即代码"（如 K8s CRD、Terraform）有什么异同？

> **考察意图：** 配置化设计考验的是抽象能力。问具体配置格式看是否真动手做过；问配置错误防范看工程稳健性。

## 四、分布式与高可用

### Q7：SchedulerX MapReduce 分治

你用 SchedulerX MapReduce 做万级商品并行巡检：

1. MapReduce 的分片策略是什么？按商品 ID hash、按类目、还是其他？
2. Map 阶段一个分片处理多少商品？怎么平衡分片大小和执行效率？
3. Reduce 阶段触发独立汇总 Job——这个"独立 Job"是通过什么机制触发的？如果 Reduce Job 失败了，Map 结果还在吗？
4. 万级商品的巡检，总体耗时多少？和原来单线程串行比提升了多少？
5. 有没有遇到过数据倾斜问题？某些分片的商品特别多、某些特别少？

> **考察意图：** MapReduce 分治模型的实战问题。Q3 的故障隔离和 Q5 的数据倾斜是区分"用过"和"理解原理"的关键。

### Q8：AI 导购员高可用设计

你做了多层面的高可用保障：备用模型、安全审核、AB 实验、降级兜底：

1. Plus 独立部署通道的备用模型——切换是自动的还是手动的？自动切换的触发条件是什么？切换延迟多少？
2. CSI 绿网安全审核是在 LLM 输出之后、用户可见之前做的吗？审核耗时多少？有没有因为这步审核导致用户感知延迟增大？
3. 多 Agent 结果为空时降级到单体 Agent——"为空"的判断标准是什么？是完全没返回还是置信度不够？
4. 灰度发布过程中，怎么观察新版本是否健康？有没有遇到过灰度期间发现新版本比旧版差、需要回滚的情况？

> **考察意图：** 高可用不是"加了兜底"就完了。问切换触发条件、审核延迟、灰度回滚这些真实运营细节，看他是否真正运维过这套系统。

## 五、记忆系统与上下文工程

### Q9：Redis 滑动窗口记忆 + 递归式意图总结

1. 滑动窗口的大小怎么定的？窗口满了之后淘汰策略是什么（LRU、FIFO、还是基于语义重要性）？
2. 递归式意图总结——"上一轮总结 + 当前输入 → 新总结"，如果某一轮总结出错了（比如意图判断错误），这个错误会不会在递归中扩散？怎么防？
3. ≤80 字的意图摘要——这个字数限制是怎么定的？有没有做过实验对比不同长度？
4. Memory 中存储的结构化元数据（resultType、keyword、intentionSummary 等），这些字段是静态 schema 还是可以动态扩展？怎么保证 schema 演进的兼容性？
5. 意图切换检测的具体逻辑是什么？举个例子说明"从购物意图切换到闲聊"是怎么检测到的？

> **考察意图：** 记忆系统是 Agent 的核心难题。递归总结的错误传播、窗口淘汰策略、意图切换检测——这些都是真正做过记忆系统才会遇到的问题。

## 六、AI Coding 实践与工程化思维

### Q10：AI Coding 落地经验

你在渠道化表达项目中沉淀了开发 skill，结合 AI Coding 插件实现"口述到代码分钟级交付"：

1. 这个 skill 具体包含什么内容？是代码模板、规则约束、还是上下文文档？能描述一下它的结构吗？
2. "分钟级交付"——从口述需求到可运行代码，实际流程是怎样的？人工在哪些环节参与？
3. AI 生成的代码质量怎么保证？有没有做 review 或自动化检查？出了 bug 怎么排查？
4. 团队其他人用过这个 skill 吗？效果怎么样？有没有推广到其他项目？
5. 你觉得 AI Coding 在当前阶段的局限性在哪？什么场景适合、什么场景不适合？

> **考察意图：** 这是一个前瞻性问题。有 AI Coding 实践经验且能反思局限性的人，说明对新工具的使用是理性的而非跟风。Q5 看他的技术判断深度。

## 面试建议

**候选人的明显优势：**
- 学历出色（985 本 + 中物院保研硕）
- 阿里核心业务（猫超）的正规军经验
- 后端工程 + AI 应用双栖能力，尤其模型微调经验稀缺
- 有 AI Coding 实践经验，对新技术敏感

**面试中需要重点验证的：**
1. **Q3-Q4（模型微调）的深度**——这是简历含金量最高也最容易被夸大或混淆角色（主导 vs 参与）的部分。追问数据构造、训练框架、评测细节，看是否亲自动手。
2. **Q1（DAG/注解驱动）是自己写的还是框架内置**——阿里内部框架（xLangChain/TPP）可能是平台团队造好的轮子，确认他是否理解其内部机制。
3. **Java 为主、LangChain 写 Java**——简历写核心语言是 Java，但 LangChain 生态以 Python 为主。确认 AI 部分的实际语言分工（Q11）。
4. **AI Coding 实践**（Q10）是加分项，但也看他是否过度依赖——现场出一个 mini 设计题看他脱离 AI Coding 后的裸写能力。

**给面试官的话：** 这是一份非常出色的 2 年经验简历。如果面试表现匹配简历内容，这是一个值得重点考虑的候选人。核心验证点是"深度是否匹配描述"——他能说清楚每个技术决策的 why 和 why not，还是只会复述 what。
