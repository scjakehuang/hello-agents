# 消息重试与死信队列（%RETRY% + %DLQ%）

消费失败怎么办？RocketMQ 的答案是**重试 16 次（带延迟退避）+ 死信兜底**。这套机制几乎覆盖了所有"我能不能让这条消息别丢"的诉求。

---

## 一、整体架构

```
Consumer 消费消息
        │
        ▼
    消费结果？
        │
    ┌───┴───────────────────────────┐
    │                                │
CONSUME_SUCCESS              RECONSUME_LATER / 抛异常
    │                                │
    ▼                                ▼
正常 ACK，offset 推进     Broker 把消息发到 %RETRY%GroupName
                                     │
                                     │ 第 N 次重试，按 N 选 delayLevel
                                     ▼
                          延迟消息机制（见 09 篇）
                                     │
                                     │ 时间到 → 还原 Topic → 重投
                                     ▼
                            Consumer 再次拉到该消息
                                     │
                              ┌──────┴──────┐
                              │             │
                          成功 ACK     再次失败
                                            │
                              重试次数 < 16？
                                  │
                              ┌───┴───┐
                              │       │
                            是 →     否 → 进 %DLQ%GroupName
                          继续重试         （死信，人工介入）
```

## 二、%RETRY% 队列

### 2.1 命名

```
重试 Topic：%RETRY%ConsumerGroup
例：
  消费组：order_consumer_group
  重试 Topic：%RETRY%order_consumer_group
```

**关键设计**：重试 Topic 是按**消费组**维度的，不是按原 Topic！

```
为什么按消费组：
  Topic-A 有 2 个消费组 group1, group2
  group1 消费失败 → 进 %RETRY%group1
  group2 消费失败 → 进 %RETRY%group2
  
  → 互不干扰，A 组重试不影响 B 组
```

### 2.2 自动订阅

```java
// PushConsumer 启动时自动订阅 %RETRY% Topic
consumer.subscribe("OrderTimeout", "*");

// 内部等价于：
consumer.subscribe("OrderTimeout", "*");
consumer.subscribe("%RETRY%order_consumer_group", "*");
```

Consumer 拉消息时同时拉两个 Topic，对业务透明。

### 2.3 重试次数与 delayLevel 映射

```
失败次数 → delayLevel → 实际延迟
   1     →    3       →    10s
   2     →    4       →    30s
   3     →    5       →    1m
   4     →    6       →    2m
   5     →    7       →    3m
   6     →    8       →    4m
   7     →    9       →    5m
   8     →    10      →    6m
   9     →    11      →    7m
  10     →    12      →    8m
  11     →    13      →    9m
  12     →    14      →    10m
  13     →    15      →    20m
  14     →    16      →    30m
  15     →    17      →    1h
  16     →    18      →    2h
  17     →            →    进死信队列

累计延迟（最多重试 16 次）：约 4 小时 46 分
```

**指数退避思想**：失败越多，等得越久。给下游故障恢复留时间。

### 2.4 Consumer 怎么标记失败

```java
// 方式 1：返回 RECONSUME_LATER
consumer.registerMessageListener(new MessageListenerConcurrently() {
    @Override
    public ConsumeConcurrentlyStatus consumeMessage(
            List<MessageExt> msgs, ConsumeConcurrentlyContext ctx) {
        try {
            doBusinessLogic(msgs);
            return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
        } catch (Exception e) {
            return ConsumeConcurrentlyStatus.RECONSUME_LATER;
        }
    }
});

// 方式 2：抛异常（也会触发重试）
throw new RuntimeException("处理失败");

// 方式 3：自定义延迟级别（ctx 上）
ctx.setDelayLevelWhenNextConsume(5);  // 下次 1 分钟后重试
```

### 2.5 顺序消费的重试

```
顺序消费（MessageListenerOrderly）：
  失败 → SUSPEND_CURRENT_QUEUE_A_MOMENT
  不进 %RETRY%，而是阻塞当前 Queue，定时重拉
  默认 1 秒后重试
  
  原因：进 %RETRY% 会破坏顺序（消息被改投递到其他时间）
```

## 三、Broker 端：消息怎么进 %RETRY%

### 3.1 ConsumerSendMsgBackProcessor

```java
// Consumer 返回 RECONSUME_LATER 后，发 RequestCode.CONSUMER_SEND_MSG_BACK
// Broker 端的处理器：
public class SendMessageProcessor {
    public RemotingCommand consumerSendMsgBack(req) {
        // ① 拿到原消息
        MessageExt origin = consumeOffsetManager.queryMessage(req.getOffset());
        
        // ② 增加重试次数
        int reconsumeTimes = origin.getReconsumeTimes() + 1;
        
        // ③ 判断是否超过最大重试次数（默认 16）
        if (reconsumeTimes > maxReconsumeTimes) {
            // 进死信队列
            newTopic = "%DLQ%" + req.getGroup();
        } else {
            // 进重试队列
            newTopic = "%RETRY%" + req.getGroup();
            
            // ④ 设置延迟级别（reconsumeTimes + 2，对应 10s 起步）
            int delayLevel = reconsumeTimes + 2;
            msg.setDelayTimeLevel(delayLevel);
        }
        
        // ⑤ 改 Topic 重新写入 CommitLog
        msg.setTopic(newTopic);
        msg.setReconsumeTimes(reconsumeTimes);
        commitLog.putMessage(msg);
    }
}
```

### 3.2 重试消息的 Topic 改写

```
原始消息：Topic = OrderTimeout
        │
        │ 消费失败
        ▼
进 CommitLog：Topic = %RETRY%order_consumer_group, delayLevel = N
        │
        │ ScheduleMessageService 到时投递
        ▼
重新写入 CommitLog：Topic = %RETRY%order_consumer_group, delayLevel = 0
        │
        │ Consumer 拉取（自动订阅了 %RETRY% Topic）
        ▼
Consumer 拿到消息，reconsumeTimes 已更新
```

## 四、%DLQ% 死信队列

### 4.1 命名

```
死信 Topic：%DLQ%ConsumerGroup
例：%DLQ%order_consumer_group
```

### 4.2 死信特征

```
• Consumer 默认不订阅 %DLQ% → 死信不会被自动消费
• 死信消息会一直保留（除非过了 fileReservedTime）
• 需要人工介入处理
```

### 4.3 怎么处理死信？

```
方案 1：管理后台手动重发
  RocketMQ Console → 选中死信 → 手动 resend 到原 Topic

方案 2：写专门的 Consumer 订阅 %DLQ%
  consumer.subscribe("%DLQ%order_consumer_group", "*");
  → 入库 + 报警 + 人工审核

方案 3：每天定时任务扫描死信
  入库到独立表，业务侧补偿
```

### 4.4 监控告警

```
关键指标：
  • %DLQ% Topic 的消息数 > 0 → 立即告警
  • %RETRY% 队列堆积量 → 大量堆积说明下游持续异常
  • Consumer 失败率（消费失败次数 / 消费总次数）
```

## 五、坑与最佳实践

### 5.1 顺序消费 vs 并发消费的重试差异

| 维度 | 并发消费 | 顺序消费 |
|---|---|---|
| 重试机制 | %RETRY% Topic + 延迟 | 阻塞当前 Queue + 1s 重试 |
| 失败影响 | 单条消息延迟重试 | 整个 Queue 暂停消费 |
| 最大重试 | 16 次 | 无限重试（除非业务退出） |
| 死信队列 | %DLQ% 兜底 | 不会进死信（除非手动退出） |

### 5.2 业务幂等性必须自己做

```
重试机制 = "消息至少消费一次"，不是"恰好一次"

可能场景：
  Consumer 处理成功 → 返回 SUCCESS 前网络中断
  → Broker 未收到 ACK
  → 触发 RECONSUME（其实业务已成功）
  → 消息被处理 2 次

→ 业务必须做幂等（用业务唯一键 + Redis SETNX / 数据库唯一索引）
```

### 5.3 不要用 RECONSUME_LATER 当业务延时

```
❌ 错误用法：
  "我想 1 分钟后处理这条消息" → 故意返回 RECONSUME_LATER
  → 重试次数会消耗，最多 16 次后进死信
  → 死信报警一直叫

✅ 正确用法：
  用延迟消息（msg.setDelayTimeLevel）
```

### 5.4 自定义重试次数

```java
// Consumer 端配置
consumer.setMaxReconsumeTimes(5);  // 默认 16，改为 5

// 或在 ctx 上自定义本次延迟
ctx.setDelayLevelWhenNextConsume(10);  // 这次失败后 6 分钟再来
```

### 5.5 重试消息的 retryTimes 怎么拿

```java
MessageExt msg = ...;
int retryTimes = msg.getReconsumeTimes();  // 0 = 第一次消费

if (retryTimes >= 3) {
    // 重试 3 次还失败 → 直接进自建死信表，别再重试
    saveToFailTable(msg);
    return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
}
```

### 5.6 死信不要永久依赖

```
死信只是兜底，不是业务"垃圾桶"
高频进死信 = 系统设计有问题

排查方向：
  • 下游服务是否长期不可用？
  • 业务逻辑是否有 bug？
  • 是否有脏数据？
  • Consumer 的处理能力是否不够（超时）？
```

## 六、和延迟消息的关系

```
重试机制 = 延迟消息的内部应用

消费失败 → Broker 给消息打 delayLevel = reconsumeTimes + 2
       → 走 SCHEDULE_TOPIC_XXXX → 时间到了重投到 %RETRY% Topic
       → Consumer 拉到再次消费

→ 重试 = 自动选 delayLevel 的延迟消息
```

---

## 七、一句话记住核心

> **消费失败 → %RETRY%Group → 延迟重试 16 次 → 还失败 → %DLQ%Group 兜底。**
>
> 重试延迟按指数退避：10s, 30s, 1m, 2m, ..., 2h，累计约 4h46m。
>
> 业务侧必须自己做幂等（消息至少消费一次，不是恰好一次）。
>
> %DLQ% 是兜底不是垃圾桶——频繁进死信说明系统有问题。
