# Broker 端长轮询 Hold 请求处理机制

这块是 RocketMQ "近实时"的核心机密。把 Broker 侧长轮询的完整链路、关键数据结构、唤醒机制、超时处理、踩坑点一次说透。

---

## 一、为什么要长轮询？三种方案对比

```
┌─────────────────────────────────────────────────────────────┐
│ 方案 A：Push（Broker 主动推）                                 │
│  Broker ──消息──▶ Consumer                                   │
│  ❌ Consumer 处理慢时 Broker 推爆它（无背压）                │
│  ❌ Broker 要维护 Consumer 处理能力，状态复杂                │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ 方案 B：短轮询（Consumer 定时拉）                              │
│  Consumer ──pull?──▶ Broker (无消息) ──no──▶                 │
│  Consumer ──sleep 1s──▶ pull──▶ ...                          │
│  ❌ 无消息时大量空请求（CPU + 带宽浪费）                     │
│  ❌ 实时性差（取决于轮询间隔）                                │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ 方案 C：长轮询（RocketMQ 采用）★                              │
│  Consumer ──pull──▶ Broker                                    │
│     有消息？                                                  │
│       是 → 立刻返回                                           │
│       否 → Broker hold 住请求最多 15s                         │
│             ├─ 期间有新消息 → 立刻唤醒返回                    │
│             └─ 15s 超时   → 返回 NO_NEW_MSG，Consumer 立刻重拉│
│  ✅ 实时性毫秒级（写入即可被消费）                            │
│  ✅ 无空请求（连接保持但不占 CPU）                            │
│  ✅ 背压天然存在（Consumer 自己控制何时 pull）                │
└─────────────────────────────────────────────────────────────┘
```

**长轮询 = 服务端把请求"挂起"，直到有数据或超时**。HTTP/2 SSE、WebSocket 替代品、Comet 都是这套思想。

## 二、整体架构：4 个核心组件协作

```
                  Consumer Pull 请求
                        │
                        ▼
   ┌───────────────────────────────────────────┐
   │ ① PullMessageProcessor                     │
   │   （Netty 业务线程池，处理 PULL_MESSAGE）   │
   │                                             │
   │   流程：                                    │
   │   1. 查 ConsumeQueue 取消息                 │
   │   2. 有消息 → 直接 channel.writeAndFlush()  │
   │   3. 无消息 → 构造 PullRequest 挂起         │
   └────────────────┬──────────────────────────┘
                    │ 无消息时
                    ▼
   ┌───────────────────────────────────────────┐
   │ ② PullRequestHoldService                   │
   │   （后台线程，定时扫描挂起的请求）           │
   │                                             │
   │   数据结构：                                │
   │   ConcurrentMap<                            │
   │     String/*topic@queueId*/,               │
   │     ManyPullRequest                        │
   │   > pullRequestTable                        │
   │                                             │
   │   行为：                                    │
   │   • 每 5s 主动扫一次（兜底）                 │
   │   • 检查每个 PullRequest 是否：             │
   │     - 已超时 → 返回 NO_NEW_MSG              │
   │     - 有新消息（offset 增长）→ 返回数据     │
   └────────────────┬──────────────────────────┘
                    │ 被动唤醒
                    ▼
   ┌───────────────────────────────────────────┐
   │ ③ NotifyMessageArrivingListener            │
   │   （消息写入后回调）                         │
   │                                             │
   │   触发点：                                  │
   │   消息写入 CommitLog → 异步分发到           │
   │   ConsumeQueue → ReputMessageService       │
   │   → 调用 listener.arriving(topic, queueId, │
   │           offset, ...)                     │
   │                                             │
   │   → 转交给 PullRequestHoldService          │
   │     的 notifyMessageArriving()             │
   └────────────────┬──────────────────────────┘
                    ▼
   ┌───────────────────────────────────────────┐
   │ ④ PullMessageProcessor.executeRequest-     │
   │   WhenWakeup()                              │
   │   （唤醒后由独立线程池重新执行 Pull 逻辑）   │
   │                                             │
   │   → 再次查 ConsumeQueue                     │
   │   → 走 PullMessageProcessor 原始流程       │
   │   → 写回 Channel                            │
   └────────────────────────────────────────────┘
```

## 四、关键数据结构详解

### 4.1 PullRequest（Broker 侧）

> ⚠️ 注意区分：**Consumer 侧也有个 PullRequest 类**（在 PullMessageService 里用），**Broker 侧的 PullRequest 是不同的类**，专门用来挂起。

```java
// org.apache.rocketmq.broker.longpolling.PullRequest
public class PullRequest {
    // 原始的 Netty 请求，唤醒后重放用
    private final RemotingCommand requestCommand;
    
    // 客户端连接 channel，唤醒后直接 writeAndFlush
    private final Channel clientChannel;
    
    // 超时控制
    private final long timeoutMillis;        // 15s（Push Consumer 默认）
    private final long suspendTimestamp;     // 挂起开始时间
    
    // 拉取参数
    private final long pullFromThisOffset;   // 客户端想拉的位点
    
    // Tag 过滤
    private final SubscriptionData subscriptionData;
    private final MessageFilter messageFilter;
}
```

## 五、唤醒机制：主动 + 被动 双保险

### 5.1 被动唤醒（实时通道）— 毫秒级延迟

```
消息写入流程：

Producer → CommitLog.putMessage()
              │
              ▼
       MappedFile 顺序写
              │
              ▼ （写完即返回 Producer，不等分发）
              │
       ReputMessageService (后台线程，1ms 循环)
              │
              ▼
       从 CommitLog 读出新消息
              │
       ┌──────┴──────┐
       ▼             ▼
  ConsumeQueue   IndexFile
   分发器          分发器
       │
       ▼
  DefaultMessageStore.doDispatch()
       │
       ▼
  messageArrivingListener.arriving(
      topic, queueId, logicOffset, tagsCode, ...)
       │
       ▼
  NotifyMessageArrivingListener.arriving()  ← Broker 启动时注入
       │
       ▼
  PullRequestHoldService.notifyMessageArriving(
      topic, queueId, maxOffset, tagsCode, msgStoreTime, ...)
       │
       ▼
  从 pullRequestTable 拿 ManyPullRequest
       │
       ▼
  ★ 关键判断逻辑：
  
  for (PullRequest pr : requests) {
      long newestOffset = maxOffset;
      
      // ① 位点判断：有新消息可拉？
      if (newestOffset > pr.getPullFromThisOffset()) {
          
          // ② tag 过滤判断（避免唤醒不订阅这个 tag 的 consumer）
          boolean match = pr.getMessageFilter()
                            .isMatchedByConsumeQueue(
                                tagsCode, propertiesMap);
          
          if (match) {
              // ③ 唤醒
              executeRequestWhenWakeup(channel, request);
              continue;
          }
      }
      
      // ④ 没新消息或不匹配 → 检查是否超时
      if (System.currentTimeMillis() >=
          pr.getSuspendTimestamp() + pr.getTimeoutMillis()) {
          executeRequestWhenWakeup(channel, request);  // 超时也唤醒
          continue;
      }
      
      // ⑤ 都不满足 → 放回，继续挂着
      replayList.add(pr);
  }
```

### 5.2 主动唤醒（兜底通道）— 最长 5s 延迟

为什么需要兜底？

```
极端情况：
  • NotifyMessageArrivingListener 因 GC/异常没触发
  • 时钟跳变导致 suspendTimestamp 异常
  • ReputMessageService 卡住（CommitLog 分发延迟）
  
→ 没有兜底，Consumer 会一直挂着不返回 → 业务雪崩
```

兜底实现：

```java
// PullRequestHoldService.run()
while (!stopped) {
    try {
        // longPollingEnable=true（默认） → 等 5s
        // longPollingEnable=false        → 等 1s（短轮询模拟）
        if (brokerController.getBrokerConfig().isLongPollingEnable()) {
            waitForRunning(5 * 1000);
        } else {
            waitForRunning(brokerController.getBrokerConfig()
                .getShortPollingTimeMills());  // 默认 1s
        }
        
        // 遍历所有挂起的 (topic, queueId)
        for (String key : pullRequestTable.keySet()) {
            String[] kArray = key.split("@");
            String topic = kArray[0];
            int queueId = Integer.parseInt(kArray[1]);
            
            // 从 MessageStore 查最新 offset
            long newestOffset = messageStore
                .getMaxOffsetInQueue(topic, queueId);
            
            // 复用同一套判断逻辑（同 5.1）
            notifyMessageArriving(topic, queueId, newestOffset);
        }
    } catch (Throwable e) {
        log.warn("PullRequestHoldService error", e);
    }
}
```

### 5.3 唤醒后为什么不直接 write？要重新走 Processor？

```java
public void executeRequestWhenWakeup(Channel channel, RemotingCommand request) {
    Runnable run = () -> {
        try {
            // ★ 不是直接返回缓存数据，而是重新查一次
            // 因为：
            //   1. 这期间又可能来了更多消息（一次性返回）
            //   2. 唤醒原因可能不准（tag 匹配错误兜底）
            //   3. 复用同一套 processRequest 逻辑（代码统一）
            
            final RemotingCommand response = 
                PullMessageProcessor.this.processRequest(
                    channel, request, false);  // ← brokerAllowSuspend=false ★
            
            if (response != null) {
                response.setOpaque(request.getOpaque());
                channel.writeAndFlush(response);
            }
        } catch (Throwable e) {
            log.error("processRequestWrapper response to client", e);
        }
    };
    
    // 提交到 pullMessageExecutor（独立线程池，不阻塞 IO）
    this.brokerController.getPullMessageExecutor().submit(
        new RequestTask(run, channel, request));
}
```

**`brokerAllowSuspend=false` 是关键**：第二次进来即使还没消息，也不再挂起，直接返回 `NO_NEW_MSG`——避免无限挂起。

## 六、客户端配合：超时怎么定？

### 6.1 两个超时的关系

```
Consumer 侧：
  pullTimeoutMillis = 30000   // ← Netty 调用超时，30s
  brokerSuspendMaxTimeMillis = 15000  // ← 告诉 Broker 挂多久，15s
  
  约束：pullTimeoutMillis > brokerSuspendMaxTimeMillis
  
  原因：
  Broker hold 15s ──┐
                    │ 15s 后必定回响应
  Netty 等 30s ─────┤
                    │ 留 15s 给网络往返 + Broker 处理
                    ▼
                  足够了
```

### 6.2 Pull Consumer 和 Push Consumer 的差异

| 维度 | DefaultMQPullConsumer | DefaultMQPushConsumer（底层也是 Pull） |
|---|---|---|
| 默认 brokerSuspendMax | 20s | **15s** |
| 默认 pullTimeout | 30s | **30s** |
| 谁触发下一次 Pull | 业务代码 | SDK 自动 |
| 实时性 | 取决于业务调用频率 | 上一次返回即立刻发下一次 |

## 七、性能与容量

### 7.1 单 Broker 能挂多少长轮询请求？

```
内存占用估算：
  PullRequest 对象本身 ≈ 1 KB（含 channel 引用 + request 对象）
  ManyPullRequest 列表开销小
  ConcurrentHashMap 节点 ≈ 64 B
  
假设 10 万 Consumer 同时挂着：
  10万 × 1KB = 100 MB
  
完全没压力（Broker 默认 8G 堆）
```

**真正的瓶颈不是挂起，是唤醒后的拉取吞吐**。

### 7.2 唤醒风暴问题

```
场景：1 万个 Consumer 同时挂着同一个 Topic 的 Q5

新消息到达 → notifyMessageArriving →
  1 万个 PullRequest 全部进 pullMessageExecutor 线程池
  → 线程池堆积 → 拉取延迟飙升 → Consumer 体验"卡顿"

缓解措施：
  ① pullMessageExecutor 默认 16+ 线程（按 CPU 数）
  ② 同 Group 内 Consumer 数 ≤ Queue 数（避免无效挂起）
  ③ Topic Queue 数充分（默认 4 不够，业务大流量调到 16/32）
```

## 八、常见踩坑

### 8.1 `longPollingEnable=false` 退化为短轮询

```bash
# broker.conf
longPollingEnable=false
shortPollingTimeMills=1000  # 短轮询的"挂起"时间，默认 1s
```

退化后：
- Broker 收到 Pull 无消息 → 挂 1s 后必返回 `NO_NEW_MSG`
- **实时性从毫秒级 → 秒级**
- 一般不开，除非客户端没法支持长连接保活

### 8.2 Broker 重启时挂起的请求怎么办？

```
Broker 优雅关闭流程：
  1. 停止接收新请求（unregister NameServer）
  2. PullRequestHoldService.shutdown() → 唤醒所有挂起请求
  3. 等待业务线程池处理完
  4. 关闭 Netty
  
Consumer 侧体验：
  • 收到 RemotingException 或 channel 断开
  • 自动重连，触发新 Pull
```

### 8.3 长轮询期间 Channel 断开

```java
// Netty 检测到连接断开 → channelInactive 事件
// PullRequestHoldService 怎么感知？
//   答：不主动感知，等唤醒时 writeAndFlush 失败再处理
//   
//   writeAndFlush(response).addListener(future -> {
//       if (!future.isSuccess()) {
//           log.warn("response to client failed, channel: {}", channel);
//       }
//   });
//
// 这些"无效"的 PullRequest 仍在 pullRequestTable 里，
// 但下次唤醒时 writeAndFlush 失败就消失了，不影响功能
```

### 8.4 Tag 过滤导致"假唤醒"

```
场景：
  Topic order，Q5 上挂了 Consumer-A (subscribe tag="pay")
  新消息来了，tag="refund"
  
notifyMessageArriving 触发：
  Broker 侧用 SubscriptionData + tagsCode 做粗过滤
  → 不匹配 → 不唤醒 Consumer-A ✓
  
但有边界情况：
  消息体里有 properties（SQL92 过滤）
  Broker 侧只能拿 tagsCode 判断，无法判断 properties
  → 唤醒 Consumer-A → Consumer-A 拉到后再过滤 → 返回 NO_MATCHED
  → 业务线程白跑一次
  
解决：尽量用 Tag 过滤，少用 SQL92
```

## 十、一句话记住核心

> **Broker 不"推"消息，而是把 Pull 请求"按住"——消息一到就松手，没到就 15s 后说"没货"。**
>
> 实现 = `pullRequestTable[topic@queueId] → ManyPullRequest` + `写入时回调唤醒` + `5s 兜底扫描`。
