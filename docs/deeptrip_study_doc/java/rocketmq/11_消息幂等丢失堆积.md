# 消息幂等、丢失与堆积（三大经典问题）

这三个问题是面试官最爱问、生产环境最容易踩坑的"老三样"。理解它们就理解了消息系统的核心权衡。

---

## 一、消息幂等

### 1.1 为什么必须做幂等？

```
RocketMQ 提供的语义：At Least Once（至少一次）
不是：Exactly Once（恰好一次）

→ 消息可能被消费多次
→ 业务必须自己做幂等
```

### 1.2 消息为什么会重复？

```
场景 1：Producer 重复发送
  Producer 调 send() 超时（其实 Broker 已写入）
  Producer 自动重试 → 同一条消息进 Broker 两次

场景 2：Consumer 重复消费
  Consumer 消费成功，但还没提交 offset → 服务挂了
  下次启动后从老 offset 拉 → 同一条消息再消费一次

场景 3：Rebalance 重复消费
  Consumer 实例数变化触发 Rebalance
  Queue 被分给新实例 → 新实例从老 offset 拉

场景 4：网络抖动 ACK 丢失
  Consumer 处理成功 → 返回 ACK 时网络抖动
  Broker 没收到 → 触发 RECONSUME
```

### 1.3 幂等方案对比

| 方案 | 实现 | 适用场景 | 优缺点 |
|---|---|---|---|
| **业务唯一键 + DB 唯一索引** | 用业务 ID（如 orderId）建唯一索引 | 写库类业务 | ✓ 强一致 ✗ 性能略低 |
| **Redis SETNX** | `SET msgKey 1 NX EX 86400` | 高频幂等校验 | ✓ 性能高 ✗ Redis 故障时不可靠 |
| **状态机** | 订单状态 PENDING→PAID 只能单向 | 状态变更类业务 | ✓ 业务自然契合 ✗ 设计要严谨 |
| **Token / 版本号** | 消息带 version，对比 DB 当前 version | 乐观锁场景 | ✓ 无中间件依赖 ✗ 业务复杂 |
| **MessageId** | RocketMQ msgId 全局唯一 | 简单去重 | ✗ Producer 重发会变 msgId，不可靠 |

### 1.4 推荐：业务唯一键 + DB 唯一索引

```sql
-- 幂等日志表
CREATE TABLE idempotent_log (
    biz_key VARCHAR(64) PRIMARY KEY,    -- 业务唯一键（orderId + msgType）
    msg_id  VARCHAR(64),
    status  TINYINT,                     -- 0=处理中 1=成功 2=失败
    create_time DATETIME,
    INDEX idx_create_time(create_time)
);

-- Consumer 处理逻辑
public ConsumeStatus consume(MessageExt msg) {
    String bizKey = msg.getKeys();  // 业务侧 Producer 时塞进去
    
    try {
        // ① 插入幂等记录
        int n = idempotentMapper.insert(bizKey, msg.getMsgId());
        if (n == 0) {
            // 已存在 → 幂等命中，直接返回成功
            return SUCCESS;
        }
        
        // ② 执行业务
        doBusiness(msg);
        
        // ③ 标记成功
        idempotentMapper.markSuccess(bizKey);
        return SUCCESS;
        
    } catch (DuplicateKeyException e) {
        return SUCCESS;  // 唯一索引冲突 = 已处理过
    } catch (Exception e) {
        idempotentMapper.markFail(bizKey);
        return RECONSUME_LATER;
    }
}
```

### 1.5 推荐：Redis SETNX（性能优先）

```java
public ConsumeStatus consume(MessageExt msg) {
    String key = "msg:processed:" + msg.getKeys();
    
    // SETNX + EX，原子操作
    Boolean ok = redis.setIfAbsent(key, "1", 24, TimeUnit.HOURS);
    if (!ok) {
        return SUCCESS;  // 已处理
    }
    
    try {
        doBusiness(msg);
        return SUCCESS;
    } catch (Exception e) {
        redis.delete(key);  // 失败回滚 → 允许重试
        return RECONSUME_LATER;
    }
}
```

**坑**：业务执行成功但还没返回时 Redis 挂了，可能丢幂等记录。可以用 **Redis + DB 双层兜底**。

## 二、消息丢失

### 2.1 三大丢失环节

```
Producer → Broker → Consumer

任何一个环节都可能丢：
  ① Producer 发送丢
  ② Broker 存储丢
  ③ Consumer 消费丢
```

### 2.2 Producer 端丢失

#### 场景

```
producer.send(msg);          // 同步发送 + 检查返回值 = 不丢
producer.sendOneway(msg);    // ★ 单向发送，发了不管 = 容易丢
producer.sendAsync(msg, cb); // 异步，回调里没处理失败 = 丢
```

#### 防丢方案

```java
// 方案 1：同步发送 + 重试
DefaultMQProducer producer = new DefaultMQProducer("group1");
producer.setRetryTimesWhenSendFailed(3);  // 同步重试 3 次
producer.setRetryAnotherBrokerWhenNotStoreOK(true);  // 失败时换 Broker

SendResult result = producer.send(msg);
if (result.getSendStatus() != SendStatus.SEND_OK) {
    // ★ 业务侧自己兜底（落库 + 定时重发）
    saveToRetryTable(msg);
}

// 方案 2：事务消息（强一致）
producer.sendMessageInTransaction(msg, null);
// 见 02_事务消息.md

// 方案 3：本地消息表（最常用兜底）
// ① 业务 + 落本地消息表（同一事务）
// ② 发 MQ → 成功后删本地记录
// ③ 定时扫表，未删除的重发
```

### 2.3 Broker 端丢失

#### 场景

```
默认 ASYNC_FLUSH + ASYNC_MASTER：
  消息写 PageCache → 返回 SUCCESS（还没刷盘）
  → 此时 OS Crash → PageCache 丢失 → 消息丢
  
  消息写 Master → 返回 SUCCESS（Slave 还没同步）
  → 此时 Master 整机故障 → 消息丢
```

#### 防丢方案

```properties
# broker.conf

# ① 同步刷盘（性能下降 10x）
flushDiskType=SYNC_FLUSH

# ② 主从同步发送（性能下降 50%）
brokerRole=SYNC_MASTER

# ③ 最强组合：SYNC_FLUSH + SYNC_MASTER
# → 消息必须刷盘到主，且主从都刷盘成功才返回 ACK
# → 单 Master 整机故障 + Slave 整机故障同时发生才会丢
# → 性能：单机 1~5W TPS（vs 默认 50W TPS）

# ④ 或使用 DLedger 集群（Raft 一致性，强一致）
enableDLegerCommitLog=true
```

**实战建议**：

```
强一致业务（金融、订单）：
  SYNC_FLUSH + SYNC_MASTER 或 DLedger
  接受性能下降

普通业务（通知、日志、埋点）：
  ASYNC_FLUSH + ASYNC_MASTER
  追求高吞吐
```

### 2.4 Consumer 端丢失

#### 场景

```
Consumer 拉到消息 → 异步线程处理 → 直接返回 SUCCESS
→ 异步线程还没跑完 → Consumer 崩溃 → offset 已提交 → 消息丢
```

#### 防丢方案

```java
// ✗ 错误：异步处理 + 立即返回
public ConsumeStatus consume(List<MessageExt> msgs) {
    asyncExecutor.submit(() -> doBusiness(msgs));  // 异步
    return SUCCESS;  // ★ 还没处理完就 ACK，丢消息
}

// ✓ 正确：同步处理完再返回
public ConsumeStatus consume(List<MessageExt> msgs) {
    try {
        doBusiness(msgs);
        return SUCCESS;
    } catch (Exception e) {
        return RECONSUME_LATER;
    }
}
```

**RocketMQ 自动提交 offset 的机制**：

```
PushConsumer：
  消费成功后，Consumer 本地更新 offset
  → 每 5 秒（persistConsumerOffsetInterval）持久化到 Broker
  → 中间 Consumer 崩溃 → 下次启动从 Broker 老 offset 拉
  → 可能重复消费 5 秒内的消息（必须做幂等）
```

### 2.5 端到端不丢的完整方案

```
Producer：
  • 同步发送 + 重试
  • 失败兜底（本地消息表）
  
Broker：
  • SYNC_FLUSH + SYNC_MASTER
  • 或 DLedger 集群
  
Consumer：
  • 同步处理完再 ACK
  • 业务幂等
  • 失败进 %RETRY%，重试 16 次还失败进 %DLQ%
  
监控：
  • Producer 发送失败率
  • Broker pageCacheRT
  • Consumer 消费延迟 + %DLQ% 大小
```

## 三、消息堆积

### 3.1 堆积的本质

```
堆积 = 生产速度 > 消费速度

监控指标：
  Diff = MaxOffset - ConsumerOffset
  Diff > N（如 10000）→ 告警
```

### 3.2 堆积的根本原因

| 原因 | 说明 | 排查 |
|---|---|---|
| **Consumer 处理慢** | 业务逻辑慢、外部依赖慢 | 看 RT、外部接口耗时 |
| **Consumer 实例数不够** | 实例 < Queue 数 | 看实例数 vs Queue 数 |
| **Producer 突发流量** | 大促、活动流量飙升 | 看 TPS 曲线 |
| **Consumer 卡死** | 死锁、FullGC、慢 SQL | 看线程栈、GC、慢查询 |
| **Rebalance 风暴** | 频繁 Rebalance 导致拉取暂停 | 看 Rebalance 日志 |
| **下游故障** | 下游 DB / Redis 不可用 | 监控下游 |

### 3.3 堆积的处理策略

#### 策略 1：扩 Consumer 实例（最常用）

```
前置条件：实例数 < Queue 数

例：Topic 有 16 个 Queue
   原 Consumer 实例 4 个 → 每个分 4 Queue
   扩到 16 个 → 每个分 1 Queue → 并发度 4x
```

**坑**：实例数 > Queue 数时，多出来的实例分不到 Queue（空跑），无效扩容。

#### 策略 2：扩 Queue 数（需停服调整）

```bash
# 命令行修改 Topic 队列数
mqadmin updateTopic -n nameserver:9876 -t TopicA -w 32

→ 现有消息按老 queueId 继续消费
→ 新消息可以分布到更多 Queue
→ Consumer 也要相应扩实例
```

#### 策略 3：提升单实例并发度

```java
// 增加消费线程数
consumer.setConsumeThreadMin(20);
consumer.setConsumeThreadMax(64);

// 增加单次拉取批量
consumer.setPullBatchSize(32);
consumer.setConsumeMessageBatchMaxSize(16);
```

#### 策略 4：异步化消费 + 业务侧补偿

```java
// 拉到立即落库 → 异步消费
public ConsumeStatus consume(List<MessageExt> msgs) {
    saveToTaskTable(msgs);  // 快速入库
    return SUCCESS;          // 立即 ACK
}

// 另起 Worker 池消费 task 表
@Scheduled
public void worker() {
    List<Task> tasks = taskMapper.pickTodo(100);
    parallelStream(tasks).forEach(this::doBusiness);
}
```

**适用场景**：业务能容忍二次异步处理；处理失败可重试。

#### 策略 5：跳过历史消息（数据可丢）

```java
// 重置 offset 到队列尾部
consumer.setConsumeFromWhere(CONSUME_FROM_LAST_OFFSET);

// 或命令行重置
mqadmin resetOffsetByTime -n nameserver:9876 \
  -g groupName -t TopicA -s now
```

**用于**：日志类消息，历史数据无价值；活动峰值过后丢掉积压。

### 3.4 堆积排查 SOP

```
告警：消费堆积 > 10W
        │
        ▼
① 看 Broker 端 dispatchBehindBytes
   → 大 = Broker 自己分发慢（罕见）
   → 正常 = 问题在 Consumer
        │
        ▼
② 看 Consumer 实例数 vs Queue 数
   → 实例 < Queue → 立即扩容
   → 实例 >= Queue → 看单实例 RT
        │
        ▼
③ 看 Consumer 端 jstack
   → 大量线程 BLOCKED → 死锁/锁竞争
   → 卡在 jdbc/http 调用 → 下游慢
   → 卡在 GC → 内存问题
        │
        ▼
④ 看下游服务 RT
   → 下游慢 → 修下游 / 加超时
   → 下游正常 → 单实例 CPU/网络
        │
        ▼
⑤ 实在搞不定 → 临时跳过老消息 + 事后补偿
```

### 3.5 避免堆积的设计原则

```
① Consumer 并发度规划：
   预估峰值 TPS / 单实例消费速度 = 实例数下限
   留 2-3 倍 buffer

② Queue 数量规划：
   Queue 数 ≥ Consumer 实例数最大值
   预留扩展空间（如 32 个 Queue 支持 1-32 个实例）

③ 业务消费 RT < 100ms：
   消费 RT 长 = 拉取间隔长 = 易堆积
   慢操作异步化

④ 限流保护：
   Consumer 端用 Sentinel/RateLimiter
   防止下游被打爆

⑤ 隔离：
   核心 Topic 独立部署 Consumer 集群
   非核心 Topic 共用
```

## 四、一句话记住核心

> **幂等**：RocketMQ 是 At Least Once，业务必须自己做幂等（业务唯一键 + DB 唯一索引 / Redis SETNX）。
>
> **丢失**：默认配置可能丢；强一致用 SYNC_FLUSH + SYNC_MASTER 或 DLedger；Consumer 必须同步处理完再 ACK。
>
> **堆积**：先看实例 vs Queue 数，再看单实例 RT，再看下游；临时方案扩容/跳消息，长期方案优化业务 + 隔离 + 限流。
