# 延迟消息的实现原理（18 级延迟 + 5.x 时间轮）

延迟消息是 RocketMQ 区别于 Kafka 的"杀手级"特性之一。订单超时关闭、定时任务、重试退避全靠它。

---

## 一、核心思路：定时任务版本的"投递"

```
Producer 发延迟消息（delayLevel=3，延迟 10 秒）
        │
        ▼
Broker 收到 → 改 Topic 为 SCHEDULE_TOPIC_XXXX
        │
        │（原始 Topic 暂存到 properties 里）
        ▼
落到 SCHEDULE_TOPIC_XXXX 的 queueId=2 的 ConsumeQueue
        │
        │（每个 delayLevel 对应一个固定 queueId）
        ▼
ScheduleMessageService（定时线程）
        │
        │ 每秒扫描每个 queue 头部
        ▼
    时间到了？
        │
        ├─ 否 → 重新调度（10ms 后再查）
        │
        └─ 是 → 还原原始 Topic + queueId
                  → 重新投递到原始 Topic 的 CommitLog
                  → 此时变成普通消息，Consumer 能拉到
```

**核心 insight**：**延迟消息 = 暂存到内部 Topic + 定时任务搬回原 Topic**。Consumer 完全感知不到延迟过程。

## 二、4.x 的 18 级延迟（固定档位）

### 2.1 默认配置

```
messageDelayLevel = 1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h
                    ↑                                                     ↑
                  level=1                                               level=18
```

```java
// Producer 设置延迟级别
Message msg = new Message("OrderTimeout", body);
msg.setDelayTimeLevel(3);  // 10 秒后投递
producer.send(msg);
```

**为什么是固定档位**：

```
设计权衡：
  ✓ 每个 level 一个独立的 ConsumeQueue 队列
  ✓ 同 level 的消息按发送时间天然有序（FIFO）
  ✓ 只需扫队列头部，不用扫全部 → O(1) 调度
  ✗ 不支持任意延迟时间（要 7 秒？只能选 5 秒或 10 秒）
```

### 2.2 SCHEDULE_TOPIC_XXXX 的特殊性

```
内部 Topic：SCHEDULE_TOPIC_XXXX

Queue 数量 = 18（每个 delayLevel 一个）
  queueId=0 → delayLevel=1 (1s)
  queueId=1 → delayLevel=2 (5s)
  queueId=2 → delayLevel=3 (10s)
  ...
  queueId=17 → delayLevel=18 (2h)

每个 queue：
  ConsumeQueue Entry 还是 20 字节
  但 tagsCode 字段被 overload 为「投递的绝对时间戳」
  
  ┌──────────────────────┬──────────────┬──────────────────────┐
  │ commitLogOffset (8B) │ msgSize (4B) │ deliveryTime (8B)    │
  └──────────────────────┴──────────────┴──────────────────────┘
                                              ↑
                                          时间到了再投递
```

### 2.3 改写过程：putMessage 时的拦截

```java
// CommitLog#putMessage（简化）
public PutMessageResult putMessage(MessageExtBrokerInner msg) {
    int delayLevel = msg.getDelayTimeLevel();
    
    if (delayLevel > 0) {
        // ★ 备份原始 Topic 和 queueId
        msg.putUserProperty(REAL_TOPIC, msg.getTopic());
        msg.putUserProperty(REAL_QID, String.valueOf(msg.getQueueId()));
        
        // 改写为 SCHEDULE Topic
        msg.setTopic(SCHEDULE_TOPIC);
        msg.setQueueId(delayLevel - 1);  // queueId = level - 1
        
        // 计算投递时间戳，写到 tagsCode
        long deliveryTime = System.currentTimeMillis() 
                          + delayLevelTable.get(delayLevel);
        msg.setTagsCode(deliveryTime);
    }
    
    // 走常规 CommitLog 写入流程
    return doAppend(msg);
}
```

### 2.4 ScheduleMessageService：定时投递

```java
// 每个 delayLevel 一个 ScheduleTask
class DeliverDelayedMessageTimerTask extends TimerTask {
    private final int delayLevel;
    private final long offset;  // 当前消费到的 ConsumeQueue offset
    
    public void executeOnTimeup() {
        // 拿到对应 delayLevel 的 ConsumeQueue
        ConsumeQueue cq = findConsumeQueue(SCHEDULE_TOPIC, delayLevel - 1);
        
        // 从 offset 开始读 entry
        SelectMappedBufferResult buffer = cq.getIndexBuffer(offset);
        
        for (int i = 0; i < buffer.getSize(); i += 20) {
            long  commitLogOffset = buffer.getLong();
            int   msgSize         = buffer.getInt();
            long  deliveryTime    = buffer.getLong();  // ← tagsCode 复用
            
            long now = System.currentTimeMillis();
            long countdown = deliveryTime - now;
            
            if (countdown > 0) {
                // ★ 时间没到 → 调度自己 countdown 毫秒后再来
                timer.schedule(new DeliverDelayedMessageTimerTask(
                    delayLevel, offset + i), countdown);
                return;
            }
            
            // 时间到了：从 CommitLog 读出原消息
            MessageExt msg = commitLog.lookMessageByOffset(
                commitLogOffset, msgSize);
            
            // ★ 还原原始 Topic 和 queueId
            msg.setTopic(msg.getProperty(REAL_TOPIC));
            msg.setQueueId(Integer.parseInt(msg.getProperty(REAL_QID)));
            msg.clearProperty(REAL_TOPIC);
            msg.clearProperty(REAL_QID);
            msg.setDelayTimeLevel(0);  // 清掉，避免循环
            
            // 重新写入 CommitLog
            putMessageBack(msg);
            
            // 推进 offset
            offset += 20;
        }
        
        // 这一轮处理完，10ms 后接着扫
        timer.schedule(new DeliverDelayedMessageTimerTask(
            delayLevel, offset), 10);
    }
}
```

### 2.5 持久化：deliverOffset 单独存

```
${ROCKETMQ_HOME}/store/config/delayOffset.json
{
  "offsetTable": {
    "1": 12345,    ← delayLevel=1 当前消费到的 ConsumeQueue offset
    "2": 6789,
    "3": 4321,
    ...
  }
}

每 10s 持久化一次
Broker 重启后从这里恢复，避免重复投递
```

## 三、为什么同 level 天然有序？

```
SCHEDULE_TOPIC_XXXX 的 queueId=2（level=3，10s 延迟）

时间线：
  T=0s    msg1 入队（投递时间 T+10）
  T=2s    msg2 入队（投递时间 T+12 = T1+10）
  T=5s    msg3 入队（投递时间 T+15）
  T=8s    msg4 入队（投递时间 T+18）

投递时间：10 < 12 < 15 < 18，严格递增
→ 只需要看队列头部第一个，头都没到时间，后面更不用看
→ ScheduleMessageService 处理超快
```

**这是固定 18 级的设计精髓**：消息按入队顺序天然按投递时间排序，不需要任何排序数据结构（堆、红黑树）。

## 四、5.x 的任意延时（时间轮 + TimerLog）

### 4.1 4.x 撑不住的场景

4.x 的 18 级延迟靠"每个 level 一个队列 + 同队列天然有序"实现 O(1) 调度，代价是延迟时间只能选 18 个离散值：

```
4.x 支持的延迟时间 = 离散的 18 个值
  1s, 5s, 10s, 30s, 1m, 2m, ..., 2h

业务想要：
  ✗ "正好 7 秒后投递"          → 没这个档位
  ✗ "2027-01-01 00:00:00 发"   → 完全做不到
  ✗ "8 小时后关单"              → 最大才 2h
```

5.x 要做的事：**让用户写一个绝对时间戳，到点就投递**。

```java
msg.setDeliverTimeMs(1830211200000L);  // 任意时间戳
```

问题来了：**几亿条延迟消息，每条投递时间都不一样，怎么管理？**

---

### 4.2 时间轮的直觉：把"按时间排序"换成"按时间分桶"

#### 朴素方案为什么不行

| 方案 | 复杂度 | 问题 |
|---|---|---|
| 全部放数组，每秒扫一遍找到点的 | O(N) | 1 亿条每秒扫一亿次 → 死 |
| 用最小堆按 deliverTime 排序，堆顶检查 | O(log N) 插入，O(1) 取最小 | 高并发插入有锁竞争；堆撑大了 GC 问题 |
| 红黑树（Java DelayQueue） | 同上 | 单机 OK，海量场景内存撑不住 |

这些方案的共同点：**数据结构和"消息条数"挂钩**。N 越大越慢。

#### 时间轮的核心想法：和"消息条数"解耦，只和"时间跨度"挂钩

```
不再问"哪条消息最早到点？"
而问"当前这一秒，有哪些消息到点了？"
```

把时间想象成一个**钟表**：

```
            ┌──────┐
       ┌────┤  0s  ├────┐
       │    └──────┘    │
   ┌───┤                ├───┐
   │9s │                │1s │
   ├───┤                ├───┤
   │8s │   tick 指针     │2s │
   ├───┤  ─────▶        ├───┤
   │7s │   (每秒走一格)   │3s │
   ├───┤                ├───┤
   │6s │                │4s │
   └───┤                ├───┘
       │    ┌──────┐    │
       └────┤  5s  ├────┘
            └──────┘
```

每一格（slot）就是一个"时间桶"，桶里挂一条**链表**，记录"该秒到点的所有消息"。

```
插入：deliverTime = T → 算出 slot 号 → 直接挂到那个 slot 的链表上
                                       O(1)，跟链表里已有几条无关

到点：tick 指针走到 slot S → 把 S 的链表整个取出来批量投递
                              O(M)，M 是这一秒到点的消息数
```

**关键认知**：插入只跟"目标时间"有关，扫描只跟"当前时间"有关，**都跟"全局有多少消息"无关**。

---

### 4.3 单层时间轮：先建立一个最小可用模型

#### 数据结构

```c
struct Slot {
    long firstPos;   // 指向 TimerLog 中链表头节点的位置
};

Slot wheel[N];       // N 个 slot 的环形数组
int  tick;           // 当前指针，每秒 +1，到 N 取模
```

把它想象成 `wheel[N]` 是一个**环形数组**：当 tick 到达 N-1，下一秒回到 0。

#### 插入：算 slot 号

```
当前时间 now = 100s
要在 107s 投递（deliverTime = 107s）
slot 号 = 107 % N

例如 N=10：
  slot = 107 % 10 = 7
  → 挂到 wheel[7] 的链表
```

#### 到点：tick 推进

```
每秒钟：
  tick = (tick + 1) % N

  取出 wheel[tick] 的整个链表
  for each entry in 链表:
      if entry.deliverTime <= now:
          投递
      else:
          放回（这是"下一圈"才到点的消息）
```

#### 单层时间轮的致命问题：**轮子要多大？**

```
N=10 的轮子能表达多远的未来？
  → 只能表达 0~9 秒

如果要 12 秒后投递：
  slot = 12 % 10 = 2，但 2 这个位置已经被 "2 秒后" 的消息占了

解决办法：在 entry 里多记一个 "round 数"：
  12 秒后 → slot=2, round=1（下一圈才投）
  2 秒后  → slot=2, round=0

扫到 slot=2 时：
  round=0 的投递
  round=1 的 round-=1 留下来
```

**问题**：如果想支持"几个月后"的延迟：

```
slot 大小 = 1 秒
要支持 30 天 = 30 × 86400 = 2,592,000 个 slot

如果只有 1 万个 slot（10000 秒 ≈ 2.7 小时）：
  30 天的消息 round 数 ≈ 260 圈
  每秒扫一次 slot，要扫 260 次才能投出去
  → 大量"我又来啦但还没到点"的无效访问
```

**单层时间轮天生扛不住"长延迟"**——这就是为什么需要层级时间轮。

### 4.4 层级时间轮：像钟表一样套圈

#### 借鉴时钟的设计

时钟有秒针、分针、时针，**精度低的指针走一圈，精度高的指针走完所有 slot**：

```
秒针（slot=60）：  每 1s 走 1 格，60 秒走完一圈
                  → 走完一圈 → 分针走 1 格
分针（slot=60）：  每 60s 走 1 格，60 分钟走完一圈
                  → 走完一圈 → 时针走 1 格
时针（slot=12）：  每 60min 走 1 格

总跨度 = 60 × 60 × 12 = 43200 秒 = 12 小时
总 slot 数 = 60 + 60 + 12 = 132（远少于 43200）
```

#### 层级时间轮的"降级"机制

```
Layer-1（秒级，slot=60，精度 1s，跨度 60s）
Layer-2（分级，slot=60，精度 60s，跨度 3600s = 1h）
Layer-3（时级，slot=24，精度 3600s，跨度 86400s = 1天）

插入时根据延迟时长选层级：
  延迟 < 60s        → 直接放 Layer-1 的对应 slot
  60s ≤ 延迟 < 1h   → 放 Layer-2
  1h ≤ 延迟 < 1d    → 放 Layer-3
```

**关键操作"降级"**：当 Layer-2 的某个 slot 到了，**不会直接投递**，而是把里面的消息**重新分配到 Layer-1**：

```
当前时间 now=00:00
有条消息 deliverTime = 00:01:30（90 秒后）
  → 落 Layer-2 的 slot=1（"1 分钟后"）

时间走到 00:01:00：
  Layer-2 的 slot=1 到点
  ↓
  把这条消息从 Layer-2 取出
  重新算：现在距投递还有 30 秒 → 落 Layer-1 的 slot=30
  ↓
时间走到 00:01:30：
  Layer-1 的 slot=30 到点 → 真正投递
```

这样**每条消息最多被"降级"几次（层数那么多），插入和到点都是 O(1)**。

> **注意**：经典理论里多层时间轮才是常见形态（Kafka、Netty HashedWheelTimer 都是这种）。RocketMQ 5.x 实际上选了"**单层时间轮 + 跨圈链表**"的简化形式（默认跨度 7 天），配合 TimerLog 持久化解决内存问题。下面看具体落地。

### 4.5 RocketMQ 5.x 的具体实现

#### 三个核心文件

```
${ROCKETMQ_HOME}/store/
├── timerwheel/
│   └── timerwheel               ← TimerWheel: 时间轮槽位（mmap 文件）
│
├── timerlog/
│   ├── 00000000000000000000     ← TimerLog: 顺序追加的索引日志
│   └── 00000000000067108864
│
└── config/
    └── timercheck               ← TimerCheckpoint: 进度持久化
```

#### TimerWheel：环形 slot 数组

```
TimerWheel 文件结构（mmap 进内存）：

  默认跨度 = 7 天 = 604800 秒
  每秒一个 slot → 604800 个 slot
  每个 slot 固定大小（约 32 字节）
  总文件大小 ≈ 19 MB（很小，常驻内存）

  ┌──────┬──────┬──────┬──────┬──────┬─...─┬──────────┐
  │slot 0│slot 1│slot 2│slot 3│slot 4│     │slot 604799│
  └──────┴──────┴──────┴──────┴──────┴─...─┴──────────┘
    ↑       ↑
    │       └─ 第 1 秒到点的消息链表头
    └── 第 0 秒到点的消息链表头

每个 slot 字段：
  ┌─────────────┬─────────┬───────────┬───────────┐
  │ firstPos    │ lastPos │ num       │ magic     │
  │ (TimerLog)  │         │ (条数)    │ (校验码)  │
  └─────────────┴─────────┴───────────┴───────────┘
   ↑
   指向 TimerLog 中"该 slot 链表头节点"的物理位置
```

#### TimerLog：消息时间索引的"链表节点池"

```
TimerLog 是顺序追加写的日志文件，每个 entry 大约 50 字节：

每个 entry：
  ┌──────────────────────────────────────────────────────┐
  │ size       (4B)   ← entry 大小                        │
  │ prevPos    (8B)   ← 同 slot 链表的上一个节点位置 ★    │
  │ magic      (4B)                                       │
  │ deliverMs  (8B)   ← 实际投递时间（毫秒）              │
  │ commitLogOffset (8B)  ← 原消息在 CommitLog 的位置     │
  │ size_of_msg (4B)                                      │
  │ hashCode   (4B)                                       │
  └──────────────────────────────────────────────────────┘

  → 同一个 slot 的多条消息形成"反向链表"
  → 不需要在 slot 里维护链表头尾，只要 lastPos
```

#### 一图看懂 Slot ↔ TimerLog 的关系

假设 slot=100 这一秒到点的有 3 条消息 m1、m2、m3：

```
TimerLog 文件（顺序追加）：

  pos=0      ┌─ m1 entry: prevPos=-1, deliverMs=..., commitLogOffset=...
  pos=50     ├─ 别的 slot 的消息
  pos=100    ├─ m2 entry: prevPos=0,  deliverMs=...    ← prev 指向 m1
  pos=150    ├─ 别的 slot 的消息
  pos=200    └─ m3 entry: prevPos=100, deliverMs=...   ← prev 指向 m2

TimerWheel：
  slot[100].lastPos = 200   ← 直接指向最后一个

链表遍历（从 lastPos 沿 prevPos 走）：
  m3 (pos=200) → m2 (pos=100) → m1 (pos=0) → END(prevPos=-1)
```

**好处**：写入只在 TimerLog 末尾追加（顺序写很快），slot 只需更新 `lastPos` 一个字段。

#### 跨"轮"怎么处理（消息超过 7 天）

5.x 默认时间轮跨度 7 天。如果用户设置 deliverTime = 8 天后呢？

```
插入时：
  delaySec = 8 * 86400 = 691200

  if delaySec >= 604800:   # 超出时间轮跨度
      slot = 604800 - 1    # 最后一格
      记一个 "round = 1"
  else:
      slot = delaySec
      round = 0

到点扫描时：
  扫到 slot=604799 链表
    round > 0 的：round -= 1，重新插入到 slot=604799
    round == 0 的：进入下一阶段判断
```

类似单层时间轮"按圈数等"。但因为最大 slot 已经很大（7 天），需要走多圈的消息很少。

### 4.6 完整链路：一条延迟消息的"一生"

#### 写入路径

```
Producer 发消息：
  msg.setDeliverTimeMs(now + 7000)   // 7 秒后投递
       │
       ▼
Broker.putMessage():
  ① 检测到有 DELIVER_MS 属性
  ② 备份原 Topic / queueId 到 properties
        REAL_TOPIC = "OrderPay"
        REAL_QID   = "0"
  ③ 改 Topic = "rmq_sys_wheel_timer", queueId = 0
  ④ 写入 CommitLog（位置 phyOffset=12345）
       │
       ▼
ReputMessageService 异步分发：
  ⑤ 把这条消息发到一个内部"待入轮"队列
       │
       ▼
TimerEnqueueGetService（专门负责把消息塞进时间轮）：
  ⑥ 读出 deliverMs = now + 7000
  ⑦ 算 slot：(deliverMs / 1000) % 604800
  ⑧ 在 TimerLog 末尾 append 一个 entry：
       prevPos = slot[slotIndex].lastPos    ← 接到之前的链尾
       deliverMs, commitLogOffset, size, ...
  ⑨ 更新 slot[slotIndex].lastPos = 新 entry 的位置
  ⑩ 更新 slot[slotIndex].num += 1
       │
       ▼
  消息进入"等待"状态
```

#### 投递路径

```
TimerDequeueWarmService（每秒预热下一秒的 slot 数据到 PageCache）

TimerDequeueGetService（核心扫描线程）：
  while true:
      now = currentTimeSecond()
      if now <= currentReadTimeMs:
          sleep(short)
          continue

      slotIndex = currentReadTimeMs % 604800
      slot = wheel[slotIndex]

      // 沿链表反向遍历
      pos = slot.lastPos
      while pos != -1:
          entry = timerLog.read(pos)

          if entry.deliverMs <= now:
              → 提交给 TimerDequeuePutMessageService
          else:
              → 跨圈消息，重新挂回 slot（特殊处理）

          pos = entry.prevPos

      currentReadTimeMs += 1000

TimerDequeuePutMessageService（专门负责把到点消息变回普通消息）：
  ① 用 commitLogOffset 从 CommitLog 取出原消息体
  ② 还原 Topic 和 queueId（从 REAL_TOPIC / REAL_QID）
  ③ 清掉 DELIVER_MS 属性
  ④ 把消息再次写入 CommitLog（这次 Topic=OrderPay，queueId=0）
  ⑤ ReputMessageService 把它分发到 OrderPay 的 ConsumeQueue
       │
       ▼
Consumer 拉到这条普通消息，对它而言完全感知不到延迟
```

#### 流程总览

```
Producer
   │  msg.deliverMs = now + 7s
   ▼
CommitLog（原 msg）  ◀────────────────┐
   │ Topic=rmq_sys_wheel_timer       │
   │ phyOffset=12345                 │
   ▼                                 │
TimerEnqueue                         │
   │                                 │  到点后：
   ▼                                 │  ① 取 entry → 拿 phyOffset
TimerLog（追加 entry）               │  ② 回 CommitLog 读消息体
   ↑↓                                │  ③ 还原原 Topic
TimerWheel slot[N] ─── tick 推进     │  ④ 重新 putMessage
   │                                 │
   ▼ 每秒扫 slot                      │
TimerDequeueGet ──── 时间到的 ────────┘
   │
   ▼
CommitLog（还原后的 msg, Topic=OrderPay）
   │
   ▼
ConsumeQueue[OrderPay/0]
   │
   ▼
Consumer
```

### 4.7 几个关键设计取舍

#### 1. 为什么精度是 1 秒，而不是 1 毫秒？

```
1 秒精度 → 7 天 = 604,800 个 slot → TimerWheel 文件 ~19MB
1 毫秒精度 → 7 天 = 604,800,000 个 slot → ~19GB

毫秒精度的代价：
  ✗ TimerWheel 文件巨大，无法常驻内存
  ✗ 99% 的 slot 是空的（业务很少需要毫秒级精确）
  ✗ 调度线程每毫秒醒一次，CPU 浪费

业务需求：
  ✓ 订单超时关闭：1 秒级误差完全 OK
  ✓ 定时通知：1 秒级误差完全 OK
  ✗ 高频交易：根本不该用 MQ

→ 1 秒是最合理的折衷
```

#### 2. 为什么用 TimerLog 而不是直接把信息塞 slot？

```
方案 A：slot 里直接存所有消息的 deliverMs + offset
  ✗ slot 大小不固定 → 无法 mmap 高效访问
  ✗ 每秒可能有几十万条 → slot 撑爆

方案 B（5.x 选的）：slot 只存"链表尾指针"，消息明细写 TimerLog
  ✓ slot 定长 → mmap 直接当数组用
  ✓ TimerLog 顺序追加 → 高吞吐
  ✓ 链表用 prevPos 反向连 → 不需要更新前面 entry
```

#### 3. 重启怎么不丢消息？

```
TimerCheckpoint 文件持久化：
  beginTimeMs              ← 时间轮起始时间
  endTimeMs                ← 时间轮当前推进到哪
  lastReadTimeMs           ← 调度线程读到哪一秒
  masterTimerLogTailOffset ← TimerLog 写到哪

每秒持久化一次

重启时：
  ① 读 timercheck 恢复 lastReadTimeMs
  ② 从 lastReadTimeMs 开始重新扫
  ③ 已投递的消息怎么办？
       看 TimerLog entry 的 magic 标记位 → "已投递"标记
       重启后扫描时跳过已投递的
```

#### 4. 高峰期处理不过来怎么办（Slot 堆积）

```
Slot[T] 这一秒挂了 100 万条消息：

  TimerDequeueGet 一个线程顺序遍历链表 → 慢
  TimerDequeuePut 一个线程串行重投 → 慢

5.x 的并发优化：
  ✓ TimerDequeueGet 多线程：把 slot 链表分段并行处理
  ✓ TimerDequeuePut 用线程池批量重投
  ✓ TimerDequeueWarm 提前 mmap 下一秒的 slot 数据进 PageCache

但根本上：单 slot 上限 ≈ 几十万 TPS（被 TimerLog 顺序写的吞吐限制）
超过这个量级 → 需要分集群、按业务拆 Broker
```

### 4.8 4.x 18 级 vs 5.x 时间轮

5.x 的时间轮也可以理解成"**动态生成队列**"，4.x 的 18 级延迟是"**静态预定义队列**"：

| 维度 | 4.x 18 级 | 5.x 时间轮 |
|---|---|---|
| **本质** | 18 个固定的 ConsumeQueue（每个 level 一队） | 60 万个 slot（每秒一队） |
| **同 level/slot 内的有序保证** | 天然有序（按入队） | 通过 deliverMs 排序 |
| **跨"队列"的有序** | 不保证 | 不保证 |
| **存储** | 复用 ConsumeQueue 机制（tagsCode 复用为 deliverMs） | 独立的 TimerWheel + TimerLog |
| **调度复杂度** | 每个 level 看队头 O(1) | 每秒扫一个 slot O(1) |
| **支持的延迟范围** | {1s, 5s, ..., 2h} 18 个值 | [1s, 7天]（默认）任意值 |
| **空间换时间** | 队列数 = 18 | 槽数 = 7×24×3600 = 60.4 万 |
| **适用场景** | 重试、退避 | 业务定时（订单关闭、提醒） |

**思维迁移**：18 级延迟相当于"按 level 分桶"，时间轮相当于"按秒分桶"。本质都是**分桶 + 桶内 FIFO**，差别只在桶的粒度和数量。

## 五、典型业务场景

### 5.1 订单超时关闭（最经典）

```
Producer：下单后立即发延迟消息（30 分钟）
  Message msg = new Message("OrderTimeoutCheck", orderId);
  msg.setDelayTimeLevel(16);  // 30 分钟（4.x）
  producer.send(msg);

Consumer：30 分钟后收到消息
  if (订单状态 == "未支付") {
      关闭订单 + 释放库存
  }
```

### 5.2 重试退避（RocketMQ 内部用）

```
Consumer 消费失败 → RECONSUME_LATER
  ↓
Broker 把消息发到 %RETRY%GroupName
  ↓
按重试次数选 delayLevel：
  第 1 次失败 → level 3 (10s 后重试)
  第 2 次失败 → level 4 (30s 后)
  第 3 次失败 → level 5 (1m 后)
  ...
  第 16 次失败 → level 18 (2h 后)
  第 17 次 → DLQ 死信队列
```

### 5.3 定时通知（5.x）

```java
// 2027-01-01 00:00:00 发新年祝福
Message msg = new Message("NewYearGreeting", body);
msg.setDeliverTimeMs(1830211200000L);  // 任意时间戳
producer.send(msg);
```

## 六、坑与注意事项

| 坑 | 说明 | 应对 |
|---|---|---|
| **延迟级别不能超过 18** | 4.x 写 `level=20` → 直接当成 0（立即投递） | 校验 level ≤ 18 |
| **delayLevel 在 Producer 设置无效** | 集群消费时 Producer 端的延迟设置不会被 Broker 拦截除非用 `producer.send` | 一定要 `setDelayTimeLevel()` |
| **重启时长延迟丢失？** | 不会，`delayOffset.json` 持久化了，CommitLog 也在 | 等 Broker 重启完，自动接着调度 |
| **大量延迟消息堆积** | SCHEDULE_TOPIC 队列变长，扫描变慢 | 监控 `dispatchBehindBytes` |
| **delayLevel 配置变更** | 修改 `messageDelayLevel` 后，老消息按老配置投递（按新配置时间会错乱） | 改配置后清空 SCHEDULE_TOPIC |
| **5.x 时间轮精度 1 秒** | 业务约定需要毫秒级精度做不到 | 接受秒级精度，业务侧补偿 |

---

## 七、一句话记住核心

> **延迟消息 = 暂存到内部 Topic SCHEDULE_TOPIC_XXXX + 定时任务到点搬回原 Topic。**
>
> 4.x：18 个固定档位 → 每个 level 一个 queue → 同 level 天然有序，扫队列头 O(1)。
>
> 5.x：时间轮 + TimerLog → 任意时间戳，1 秒精度。
>
> Consumer 完全感知不到延迟过程，拉到的就是普通消息——延迟纯粹是 Broker 的事。
