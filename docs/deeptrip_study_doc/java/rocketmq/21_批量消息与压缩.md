# 批量消息与压缩（吞吐优化两板斧）

发 100 条消息，是分 100 次 send 还是 1 次 sendBatch？消息体 100KB 要不要压缩？这两个选择对吞吐影响巨大。

---

## 一、批量发送（MessageBatch）

### 1.1 单条 vs 批量

```
单条发送：
  for (int i = 0; i < 100; i++) {
      producer.send(messages[i]);   // 100 次网络往返
  }
  
  网络：100 次 RT × 5ms = 500ms
  Broker：100 次写入操作
  
批量发送：
  producer.send(messages);          // 1 次网络往返
  
  网络：1 次 RT × 8ms = 8ms（数据稍大）
  Broker：1 次批量写入（连续追加）
  
→ 吞吐提升约 30 倍
```

### 1.2 API 使用

```java
// 准备一批消息
List<Message> messages = new ArrayList<>();
for (int i = 0; i < 100; i++) {
    messages.add(new Message("OrderTopic", body));
}

// 批量发送
SendResult result = producer.send(messages);
```

### 1.3 批量消息的限制

```
✗ 所有消息必须同一 Topic
✗ 所有消息不能是延迟消息
✗ 不能是事务消息
✗ 批量总大小 ≤ 4MB（messageMaxSize）
✗ 同一批消息要么全成功要么全失败（不支持部分成功）
```

### 1.4 自动分批

```java
// 工具方法：超过 4MB 自动分批
public List<List<Message>> listSplitter(List<Message> messages, int sizeLimit) {
    List<List<Message>> result = new ArrayList<>();
    List<Message> currentBatch = new ArrayList<>();
    int currentSize = 0;
    
    for (Message msg : messages) {
        int msgSize = msg.getBody().length + msg.getTopic().getBytes().length + 20;
        
        if (currentSize + msgSize > sizeLimit) {
            // 当前批次满了
            result.add(currentBatch);
            currentBatch = new ArrayList<>();
            currentSize = 0;
        }
        currentBatch.add(msg);
        currentSize += msgSize;
    }
    if (!currentBatch.isEmpty()) {
        result.add(currentBatch);
    }
    return result;
}

// 使用
for (List<Message> batch : listSplitter(allMessages, 1024 * 1024 * 3)) {
    producer.send(batch);
}
```

### 1.5 批量消息的存储

```
Broker 收到 MessageBatch：
  ① 拆开成多个独立 MessageExt
  ② 逐条写入 CommitLog（仍然每条一个 entry）
  ③ 每条独立生成 ConsumeQueue entry
  
→ Consumer 拉到的是单条消息（透明）
→ 批量只是"发送优化"，存储不变
```

### 1.6 批量消息的 ID

```
SendResult result = producer.send(messages);

// 单条发送：result.getMsgId() = 单个 ID
// 批量发送：result.getMsgId() = 多个 ID 用逗号拼接

System.out.println(result.getMsgId());
// 例：AC110001000001AABBCC,AC110001000001AABBCD,...
```

## 二、消息压缩

### 2.1 自动压缩规则

```java
// DefaultMQProducer 默认配置
private int compressMsgBodyOverHowmuch = 4096;  // 4KB
private int zipCompressLevel = 5;                // 0-9，默认 5

// 发送时自动判断
if (msg.getBody().length > compressMsgBodyOverHowmuch) {
    // 用 GZIP 压缩 body
    byte[] compressed = compress(msg.getBody());
    msg.setBody(compressed);
    msg.setSysFlag(msg.getSysFlag() | MessageSysFlag.COMPRESSED_FLAG);
}
```

### 2.2 压缩算法

```
4.x：固定 GZIP（Java DeflaterOutputStream）
  • 压缩比高（约 50%）
  • CPU 开销大

5.x：支持多种算法
  • GZIP
  • LZ4（快但压缩比低）
  • Zstandard / ZSTD（平衡）

配置：
  msg.putUserProperty("compressType", "zstd");
```

### 2.3 压缩开销

| 算法 | 压缩比 | 压缩速度 | 解压速度 | CPU 占用 |
|---|---|---|---|---|
| GZIP | 50% | 100MB/s | 300MB/s | 高 |
| LZ4 | 70% | 500MB/s | 2GB/s | 低 |
| ZSTD | 50% | 300MB/s | 1GB/s | 中 |

### 2.4 压缩后的存储和传输

```
压缩流程：
  Producer：
    body (10KB) → GZIP 压缩 → compressed (3KB) → 网络传输
    SysFlag |= COMPRESSED_FLAG
        ↓
  Broker：
    存储原样存（不解压）
    CommitLog 中是 3KB compressed
        ↓
  Consumer：
    拉到 3KB compressed + 看到 COMPRESSED_FLAG
    → GZIP 解压 → 业务拿到 10KB body
```

**节省空间和带宽**：

```
未压缩：
  100 万条 × 10KB = 10 GB（存储 + 传输）

GZIP 压缩：
  100 万条 × 3KB = 3 GB（节省 70%）
```

## 三、Consumer 端批量

### 3.1 PullBatchSize（每次拉多少条）

```java
consumer.setPullBatchSize(32);  // 默认 32
```

- 网络往返减少
- 但单次拉取 RT 增加（要等够 32 条或长轮询超时）

### 3.2 ConsumeMessageBatchMaxSize（每次回调消费多少条）

```java
consumer.setConsumeMessageBatchMaxSize(16);  // 默认 1
```

```java
// 单条消费（默认）：
public ConsumeStatus consumeMessage(List<MessageExt> msgs, ...) {
    // msgs.size() == 1
    process(msgs.get(0));
}

// 批量消费（设了 batchMaxSize=16）：
public ConsumeStatus consumeMessage(List<MessageExt> msgs, ...) {
    // msgs.size() 最多 16
    // 业务可以批量处理：批量插库、批量调外部接口
    batchProcess(msgs);
}
```

**适用场景**：

```
✓ 业务可以批量处理（批量 INSERT、批量调用）
  → 大幅减少 DB / RPC 次数
  
✗ 不要让批量太大
  → 批量内部出错难处理（部分成功难回滚）
  → 单条出错全批 RECONSUME_LATER → 反复消费
```

## 四、批量 + 压缩组合效果

### 4.1 场景测试

```
场景：发 1 万条订单消息，每条 5KB

方案 A：单条 + 不压缩
  网络：10000 次 × 5KB = 50MB
  时间：10000 × 5ms RT = 50 秒
  Broker 写入：10000 次

方案 B：批量（每批 100 条，共 100 批）+ 不压缩
  网络：100 次 × 500KB = 50MB
  时间：100 × 8ms = 0.8 秒
  Broker 写入：100 次

方案 C：批量 + GZIP 压缩
  网络：100 次 × 150KB = 15MB
  时间：100 × 6ms = 0.6 秒
  + Producer CPU：压缩 50MB 数据
  + Consumer CPU：解压 50MB 数据

→ 吞吐：方案 C > B >> A
→ CPU 开销：方案 C > B = A
```

### 4.2 选型决策树

```
消息体 < 4KB：
  ✓ 批量发送
  ✗ 压缩（自动跳过）

消息体 4KB ~ 1MB：
  ✓ 批量发送（注意 4MB 上限）
  ✓ 压缩（默认开启）

消息体 > 1MB：
  ⚠ 单条发送（容易超 4MB 批上限）
  ✓ 压缩必开
  考虑：拆分大消息 或 用对象存储传 URL

发送频率 > 100 TPS：
  ✓ 必须批量（不然 Producer CPU 都不够）
```

## 五、批量的实现细节

### 5.1 MessageBatch 的协议格式

```
MessageBatch 序列化后：

┌──────────────┬──────────────┬──────────────┬──────────────┐
│ Length(4B)   │ Message1     │ Message2     │ ... MessageN  │
└──────────────┴──────────────┴──────────────┴──────────────┘

每个 Message：
┌──────────────┬──────────────┬──────────────┐
│ Body         │ Properties   │ ...           │
└──────────────┴──────────────┴──────────────┘

→ 实际上是把多个 Message 的字节流拼起来
→ Broker 收到后逐条解析、逐条写 CommitLog
```

### 5.2 Broker 处理批量

```java
// SendMessageProcessor
public RemotingCommand processRequest(req) {
    // 判断是普通消息还是批量
    if (isBatch(req)) {
        return handleBatchMessage(req);
    }
    return handleSingleMessage(req);
}

private RemotingCommand handleBatchMessage(req) {
    MessageExtBatch batch = parseBatch(req);
    
    // ★ 整批写入 CommitLog（原子操作）
    PutMessageResult result = commitLog.putMessages(batch);
    
    // 返回所有消息的 msgId
    return buildBatchResponse(result);
}
```

### 5.3 批量写入的优化

```
CommitLog.putMessages()：
  ① 计算总大小（确保 < 一个 MappedFile 剩余空间）
  ② 一次性获取 PutMessage 锁
  ③ 连续追加多个消息到 MappedFile
  ④ 一次性释放锁

vs 单条循环写：
  for (msg in batch) commitLog.putMessage(msg);
  → 每条都要获取释放锁
  → 锁争用激烈

→ 批量写入是性能优化的关键
```

## 六、坑与最佳实践

### 6.1 批量大小不是越大越好

```
✗ 一次发 1 万条 → 单次请求 50MB
  → 网络传输慢（5G 带宽下要 80ms）
  → 失败重试代价巨大
  → 单条出错全批失败

✓ 一次发 50~500 条
  → 平衡吞吐和失败影响
```

### 6.2 批量内部顺序

```
批量发送的消息：
  ✓ 同一批内顺序写入 CommitLog
  ✓ 同 queueId 的消息相邻
  ✗ 不同 queueId 的消息可能交错

→ 如果要顺序：所有消息必须用 MessageQueueSelector 选同一个 Queue
```

### 6.3 压缩开关时机

```java
// 关闭压缩（小消息或高 CPU 场景）
producer.setCompressMsgBodyOverHowmuch(Integer.MAX_VALUE);

// 强制压缩（所有消息都压）
producer.setCompressMsgBodyOverHowmuch(0);
```

### 6.4 压缩算法选择

```
高 CPU 富余 + 网络紧张 → GZIP（压缩比最高）
低 CPU 紧张 + 吞吐优先 → LZ4
平衡选择 → ZSTD
```

### 6.5 批量消费的事务问题

```java
public ConsumeStatus consumeMessage(List<MessageExt> msgs, ...) {
    // ✗ 错误：部分成功部分失败怎么办？
    for (MessageExt msg : msgs) {
        try {
            process(msg);
        } catch (Exception e) {
            // 整批 RECONSUME_LATER 会导致已成功的也被重消
        }
    }
    
    // ✓ 正确：要么全部成功（用事务），要么全部不处理
    try {
        beginTransaction();
        for (MessageExt msg : msgs) {
            process(msg);
        }
        commit();
        return SUCCESS;
    } catch (Exception e) {
        rollback();
        return RECONSUME_LATER;
    }
}
```

## 七、监控与排查

### 7.1 监控指标

```
Producer 端：
  • 单条 send RT
  • 批量 send RT
  • 批量大小（平均/最大）
  • 压缩比

Broker 端：
  • Topic 平均消息大小
  • CommitLog 写入 RT
  • PageCache 使用率

Consumer 端：
  • 单次拉取条数
  • 消费 RT（单条/批量）
```

### 7.2 优化排查 SOP

```
高吞吐场景吞吐上不去：
  ① 看 Producer send RT
     > 10ms → 批量没开启或批太小
     → 优化为批量发送
     
  ② 看消息平均大小
     > 100KB → 压缩没开启
     → 启用 GZIP
     
  ③ 看 Consumer 拉取频率
     频繁拉取小批 → pullBatchSize 调大
     
  ④ 看 Broker PageCache 命中率
     低 → 内存不够，加机器
```

## 八、一句话记住核心

> **批量发送**：合并多次 send 为一次 RPC，吞吐提升 10~30 倍，但限制：同 Topic + 非延迟 + 非事务 + 单批 ≤ 4MB。
>
> **压缩**：> 4KB 自动 GZIP 压缩（4.x），5.x 支持 LZ4/ZSTD，节省 50~70% 网络带宽和存储。
>
> **Consumer 批量消费**：pullBatchSize 控制单次拉取条数，consumeMessageBatchMaxSize 控制单次回调条数，业务侧批量插库/调用大幅降低 DB/RPC 压力。
>
> 三者组合：吞吐 ↑↑↑、CPU ↑、网络 ↓↓↓——大流量场景必备的三大调优手段。
