## 二、四大角色：能力、特点、为什么这么设计

### 1. NameServer — 路由注册中心（**为什么不用 ZooKeeper？**）

| 维度 | 说明 |
|---|---|
| **职责** | 只做两件事：① 维护 Broker 集群路由表 ② 给客户端提供查询 |
| **关键特性** | **无状态**（数据全在内存）+ **节点互不通信**（不做主从、不选举） |
| **为什么不用 ZK** | RocketMQ 需要的是「AP」可用性而非「CP」一致性；ZK 强一致带来的写性能和运维复杂度对 MQ 路由没必要 |
| **运维代价** | 极低，挂一台不影响（客户端会重连其它节点） |
| **生产部署** | 一般 2~3 台，独立部署或与 Broker 混布都行 |

> **类比**：NameServer 就是「电话簿」，电话簿坏一本不影响打电话——客户端缓存了路由 30s，期间 NS 全挂也能继续发收消息。

### 2. Broker — 存储与转发核心

```
┌──────────────────────────────────────────────────────────┐
│                    Broker 内部模块                         │
│                                                            │
│  ┌──────────────────────────────────────────────────┐    │
│  │ Remoting Module（Netty）                          │    │
│  │  • 处理 Producer 发送、Consumer 拉取的网络请求    │    │
│  └──────────────────────────────────────────────────┘    │
│                       │                                    │
│  ┌──────────────────────────────────────────────────┐    │
│  │ Client Manager / Producer Manager / Consumer Mgr  │    │
│  │  • 维护连接、消费者组、订阅关系                    │    │
│  └──────────────────────────────────────────────────┘    │
│                       │                                    │
│  ┌──────────────────────────────────────────────────┐    │
│  │ Store Module（核心存储引擎）                       │    │
│  │   CommitLog + ConsumeQueue + IndexFile            │    │
│  │   + MappedFile（mmap）+ 刷盘服务                   │    │
│  └──────────────────────────────────────────────────┘    │
│                       │                                    │
│  ┌──────────────────────────────────────────────────┐    │
│  │ HA Service（主从复制）                             │    │
│  └──────────────────────────────────────────────────┘    │
│                       │                                    │
│  ┌──────────────────────────────────────────────────┐    │
│  │ 定时服务：刷盘 / 清理过期文件 / Slave 同步状态     │    │
│  └──────────────────────────────────────────────────┘    │
└──────────────────────────────────────────────────────────┘
```

**Broker 组（BrokerGroup）的概念**

- 同一 `brokerName` 下的 Master + Slave(s) 算**一组**
- **brokerId = 0 是 Master，> 0 是 Slave**
- 一个集群有多个 BrokerGroup，**Topic 的 MessageQueue 会被分散到各 Group 的 Master**，实现写入水平扩展
- 传统主从架构下 **Slave 不能自动顶替 Master**，要么手动切，要么用 DLedger（Raft）模式

### 3. Producer — 生产者

| 能力 | 说明 |
|---|---|
| **发送模式** | 同步（最常用）/ 异步（回调）/ 单向（fire-and-forget，日志类场景） |
| **路由选择** | 客户端拿到 Topic 的 MessageQueue 列表后**本地轮询**，故障时自动剔除 |
| **故障规避** | 开启 `sendLatencyFaultEnable` 后会按上次延迟惩罚慢 Broker |
| **ProducerGroup** | **普通消息**里基本无意义；**事务消息**里用于状态回查时找到原 Producer |

### 4. Consumer — 消费者

| 维度 | 选项 |
|---|---|
| **消费模型** | **集群消费 CLUSTERING**（同 Group 内分摊，最常用）/ **广播消费 BROADCASTING**（每节点全收） |
| **拉取方式** | 底层都是 **Pull + 长轮询**；`PushConsumer` 是 SDK 在 Pull 之上封装的"看似推"的体验 |
| **消费顺序** | `MessageListenerConcurrently`（并发，吞吐高）/ `MessageListenerOrderly`（顺序，单 Queue 串行） |
| **offset 存储** | 集群消费 → Broker（`CONSUMER_OFFSET` 文件）；广播消费 → 本地文件 |
| **Rebalance** | 客户端 20s 触发一次，按 Queue 数和 Consumer 数重新分配 |

## 三、核心概念关系图：Topic / Queue / Tag

> 这是最容易混淆但又最关键的一张图，决定了发消息怎么"分片"、消费怎么"并行"。

```
                           ┌────────────────────┐
                           │   Topic = order    │   ← 业务主题，逻辑概念
                           │   （订单事件流）     │
                           └─────────┬──────────┘
                                     │ 默认 16 个 MessageQueue
                                     │ 均匀分布在 Broker Group A/B
            ┌────────────────────────┼────────────────────────┐
            ▼                        ▼                        ▼
   ┌────────────────┐       ┌────────────────┐       ┌────────────────┐
   │ Broker Group A │       │ Broker Group A │       │ Broker Group B │
   │  brokerName=A  │       │  brokerName=A  │       │  brokerName=B  │
   │                │       │                │       │                │
   │  Queue-0       │       │  Queue-1       │       │  Queue-8       │
   │  Queue-2       │       │  Queue-3       │       │  Queue-9       │
   │  ...           │       │  ...           │       │  ...           │
   │  Queue-7       │       │  Queue-7       │       │  Queue-15      │
   └────────────────┘       └────────────────┘       └────────────────┘
            │                        │                        │
            └────────────────────────┼────────────────────────┘
                                     ▼
                          ┌──────────────────────┐
                          │  消息体内可带 Tag     │  ← Broker 侧过滤
                          │   create / pay /     │     消费端 subscribe
                          │   refund / cancel    │     ("order","pay||refund")
                          └──────────────────────┘
```

**三层关系记忆口诀**

| 层级 | 类比 | 控制什么 |
|---|---|---|
| **Topic** | 数据库 = 业务库 | 一类业务消息的集合 |
| **MessageQueue** | 表分片 = 物理分区 | **并行度的上限**（生产/消费并发都受它限制） |
| **Tag** | 行级标签 | 同 Topic 下的子分类过滤，**避免开 N 个 Topic** |

**一个常见踩坑**：Consumer 实例数 > MessageQueue 数 → 多出来的实例**永远拉不到消息**（Queue 不会被两个 Consumer 同时消费）。所以扩容时先扩 Queue 再扩 Consumer。

## 四、消息发送端到端流程（含路由发现）

```
[Producer 启动]
     │
     │ ① 启动时连一个 NameServer，拉所有 Broker 路由
     ▼
┌─────────────────────────┐
│ 本地 TopicRouteData 缓存 │  ◀──── 每 30s 后台线程刷新
│  order →                 │
│   Broker A: [Q0..Q7]    │
│   Broker B: [Q8..Q15]   │
└─────────────────────────┘
     │
     │ ② 业务调用 send(msg)
     ▼
[选 MessageQueue]
   • 默认：轮询 + 故障规避
   • 顺序：MessageQueueSelector（按 hash(orderId)）
   • 事务：先发 Half 消息
     │
     │ ③ 找到该 Queue 所在 Broker 的 Master 地址
     ▼
[Netty 长连接 send → Master Broker]
     │
     ▼
┌──────────────────────────────────────────┐
│ Broker 处理                                │
│  ④ 校验 Topic / 权限 / 大小                │
│  ⑤ 顺序追加写 CommitLog（PageCache）       │
│  ⑥ 按刷盘策略决定何时 ACK                  │
│  ⑦ 按复制策略决定何时 ACK                  │
│  ⑧ 后台异步：分发到 ConsumeQueue / Index   │
└──────────────────────────────────────────┘
     │
     │ ⑨ ACK → Producer
     ▼
[业务拿到 SendResult]
   • SEND_OK
   • FLUSH_DISK_TIMEOUT     ← SYNC_FLUSH 超时
   • FLUSH_SLAVE_TIMEOUT    ← SYNC_MASTER 超时
   • SLAVE_NOT_AVAILABLE
```

**重要**：⑤ 完成后消息就在内存里能查到，但**真正"安全"取决于刷盘和复制策略组合**（详见 `04_主从同步与刷盘.md`）。

## 五、消息消费端到端流程（含 Rebalance）

```
[Consumer 启动]
     │
     │ ① 注册到 Broker，加入 ConsumerGroup
     │ ② 每 20s 触发一次 Rebalance
     ▼
┌──────────────────────────────────────────────┐
│ Rebalance 算法（默认 AllocateMessageQueue-    │
│ AveragelyByCircle 平均轮询）                  │
│                                                │
│  Topic 有 16 个 Queue                          │
│  ConsumerGroup 内有 4 个实例                   │
│  → 每个实例分 4 个 Queue                       │
│                                                │
│  Consumer-1 → Q0,Q1,Q2,Q3                     │
│  Consumer-2 → Q4,Q5,Q6,Q7                     │
│  Consumer-3 → Q8,Q9,Q10,Q11                   │
│  Consumer-4 → Q12,Q13,Q14,Q15                 │
└──────────────────────────────────────────────┘
     │
     │ ③ 对每个分配到的 Queue 启动 PullRequest
     ▼
┌──────────────────────────────────────────────┐
│ 长轮询拉取                                     │
│   Consumer → Broker pullMessage(Q, offset)    │
│   ┌─有新消息──→ 立刻返回                       │
│   └─无新消息──→ Broker hold 住请求最多 15s     │
│                  期间有新消息立刻唤醒返回      │
└──────────────────────────────────────────────┘
     │
     │ ④ 业务方 MessageListener.consume()
     ▼
[消费结果]
   • CONSUME_SUCCESS              → 提交 offset
   • RECONSUME_LATER（并发）       → 进重试队列 %RETRY%group
   • SUSPEND_CURRENT_QUEUE（顺序） → 暂停 Queue 重投
     │
     ▼
[offset 提交]
   • 集群消费：上报 Broker，持久化 consumerOffset.json
   • 广播消费：写本地文件
```

**重试与死信**

```
正常 Topic：order
   │ 业务返回 RECONSUME_LATER
   ▼
重试 Topic：%RETRY%ConsumerGroupName
   │ 按 18 个梯度延迟（1s, 5s, 10s ... 2h）
   │ 默认最多 16 次
   ▼
死信 Topic：%DLQ%ConsumerGroupName
   │ 需要人工介入或专门的 DLQ 消费者
```

## 六、生产部署形态（推荐）

### 形态 A：传统主从（4.5 之前主流，现在仍很多）

```
┌─────────────┐  ┌─────────────┐
│ NameServer1 │  │ NameServer2 │      （2 台够用，再多冗余）
└─────────────┘  └─────────────┘

┌───────────────────────────┐  ┌───────────────────────────┐
│  Broker Group A           │  │  Broker Group B           │
│  Master-A ←SYNC→ Slave-A  │  │  Master-B ←SYNC→ Slave-B  │
└───────────────────────────┘  └───────────────────────────┘

   优点：简单、性能高
   缺点：Master 挂了需要人工或脚本切换
```

### 形态 B：DLedger Raft（4.5+，新部署推荐）

```
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│ NameServer1 │  │ NameServer2 │  │ NameServer3 │
└─────────────┘  └─────────────┘  └─────────────┘

┌───────────────────────────────────────────────────┐
│  DLedger Group A (3 节点 Raft)                     │
│   Node-A1 (Leader) ── Node-A2 ── Node-A3          │
└───────────────────────────────────────────────────┘

┌───────────────────────────────────────────────────┐
│  DLedger Group B (3 节点 Raft)                     │
└───────────────────────────────────────────────────┘

   优点：自动选主、强一致
   缺点：每个 Group 至少 3 台，机器成本 ×1.5
```

### 形态 C：RocketMQ 5.x 存算分离（Proxy + Broker）

```
                     ┌────────────────┐
   gRPC / Remoting   │     Proxy      │   ← 无状态，水平扩展
   ──────────────▶   │   (5.x 新增)   │      支持 gRPC 协议
                     └────────┬───────┘      支持多协议接入
                              │
                     ┌────────▼───────┐
                     │   Broker 集群   │   ← 专注存储
                     └────────────────┘

   优点：客户端协议解耦、易上云、多语言友好
   场景：新业务、跨语言团队、云原生部署
```

## 七、一张表看清"为什么 RocketMQ 这么设计"

| 设计点 | 选择 | 为什么 |
|---|---|---|
| 注册中心 | 自研 NameServer（无状态） | 路由不需要强一致，避免 ZK 复杂度 |
| 存储 | 所有 Topic 共用 CommitLog | 顺序写性能拉满，避免随机 IO |
| 索引 | ConsumeQueue + IndexFile | 既能按 Topic+Queue 顺序消费，又能按 Key 检索 |
| 网络 | Netty + 长连接 | 高并发低延迟 |
| 拉取 | 长轮询（Pull 伪装 Push） | 兼顾实时性（毫秒级）和服务端可控（背压） |
| 重试 | 独立 %RETRY% Topic + 18 级延迟 | 避免阻塞正常消费，业务无感知 |
| 顺序 | 同 Key → 同 Queue + Queue 加锁 | 用分区有序换吞吐，全局有序代价太大 |
| 事务 | Half + 回查 | 不依赖业务侧 XA，弱依赖即可保证一致性 |
