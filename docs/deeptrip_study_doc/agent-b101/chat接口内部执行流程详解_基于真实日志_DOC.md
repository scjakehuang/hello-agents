### 3.2 每个任务的详细说明

#### 任务 1: 语言识别 (Language Detection)

```python
# 日志: [test123_lang] 开始语言识别: 成都三日游
# 日志: [test123_lang] 语言识别成功: 简体中文 (耗时10ms)
```

这个任务不调用大模型，而是用规则匹配判断输入语言。因为"成都三日游"包含中文字符，直接判定为简体中文。

#### 任务 2: 意图识别 (Intent Detection)

```
输入 → qwen3-next-80b-a3b-instruct → 输出

┌─────────────────────────────────────────────────────┐
│ 输入 (prompt):                                      │
│   {'role': 'user', 'content': '成都三日游'}           │
│                                                     │
│ 输出 (LLM 返回):                                     │
│   <thinking>                                        │
│   用户重复询问成都三日游，此前已提供详细路线，          │
│   本次为重复请求，但未指定具体线路，仍属路线不明确。     │
│   </thinking>                                       │
│   <intent>                                          │
│   旅行规划-路线不明确                                  │
│   </intent>                                         │
│                                                     │
│ 解析结果: intent_list = ["旅行规划-路线不明确"]         │
│ 首token延迟(first token time): 2.5505秒               │
└─────────────────────────────────────────────────────┘
```

关键发现：LLM 从历史对话中推断出这是"重复询问"——之前已经问过成都三日游，所以意图是"路线不明确的旅行规划"。

#### 任务 3: 广告意图识别 (Ad Intent Detection)

```
日志: [test123_ad_intent] 开始广告意图识别, user_history_count=7
日志: [test123_ad_intent] 广告意图识别成功: 非广告意图
```

判断用户是否在进行商业查询（需要推送广告/营销活动）。这里检测到"非广告意图"，不会插入广告卡片。

#### 任务 4: Query 改写 (Query Rewriting)

```
输入 prompt 中包含对话历史 context
     │
     ▼
qwen3-next-80b-a3b-instruct 判断
     │
     ▼
输出: "成都三日游" (无需改写，因为查询本身信息已完整)
```

首token时间: 2.0124秒。改写的目的是：如果用户说"那个地方呢"这种指代不明的查询，就从历史对话中补充指代信息。

#### 任务 5: 路由识别 (Router Detection) - 核心决策

```
                       路由识别流程
                            │
                            ▼
┌──────────────────────────────────────────────────────────────┐
│ 输入包含:                                                     │
│  1. 所有子 Agent 的描述                                        │
│     - universal_agent: 通用Agent，处理复合需求                   │
│     - route_planning_agent: 行程规划，详细但慢                   │
│     - route_recommend_agent: 线路召回，快但有限                   │
│     - destination_recommend_agent: 目的地推荐                    │
│     - flight_agent: 机票查询                                    │
│     - train_agent: 火车票查询                                   │
│     - hotel_agent: 酒店查询                                     │
│  2. 完整历史对话 (之前已有成都三日游的详细回答)                     │
│  3. 当前 query: "成都三日游"                                    │
│                            │                                   │
│                            ▼                                   │
│  LLM 思考过程:                                                 │
│  <thinking>                                                   │
│  用户再次询问"成都三日游"，此前已由 route_planning_agent         │
│  提供完整详细行程，需求明确且已有优质方案，无需重复规划。          │

│                            │                                   │
│                            ▼                                   │

```

**这是整个请求流程中最关键的决策点**。路由选择 `universal_agent` 而不是 `route_planning_agent`，意味着系统认为用户是在重复之前的查询，直接用通用 Agent 处理即可，不需要走完整的行程规划子循环。

#### 任务 6: Query 洞察 (Query Insight) - 超时 ⚠️

```
日志: WARNING - [test123_insight] Query Insight 生成超时（3.0秒）
结果: query_insight = None
```

这是本次请求中唯一出错的任务。Query 洞察的目的是生成对用户查询的"深层理解"（例如用户可能隐含的偏好），但由于 LLM 响应超过 3 秒阈值被判定超时，返回了 `None`。系统对此有容错处理，不会阻塞后续流程。

#### 任务 7: 搜索分发 (Query Dispatch)

```
日志: QueryDispatch 完成: queries=2个
      detail=['route:成都三日游行程安排', 'note:成都三日游攻略 游记体验']
      preference=['relevance', 'diversity']
```

将用户的自然语言查询转换为结构化的搜索计划：
- `route` 类型：搜索行程安排相关内容
- `note` 类型：搜索游记、攻略体验

### 4.2 状态机主循环架构

agent-b101 的状态机是一个双层架构（面向 Python 初学者，这里只展示主循环的简化版本）：

```
                    ┌─────────────────────────────┐
                    │     AgentLoop.run()          │
                    │     while True:  (主循环)      │
                    └─────────────┬───────────────┘
                                  │
            ┌─────────────────────┼─────────────────────┐
            │                     │                     │
            ▼                     ▼                     ▼
   ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
   │DEFAULT_STATE │     │LLM_INFERENCE │     │POST_PROCESS  │
   │ 准备数据      │ ──→ │ 调用大模型    │ ──→ │ 后处理        │
   │ 构建prompt   │     │ 流式输出      │     │ 保存到ES      │
   │ travel分析   │     │ FSM解析标签   │     │ 发送MQ通知    │
   └──────────────┘     └──────────────┘     └──────────────┘
                                                   │
                                                   ▼
                                              SSE finsh
                                             (流结束信号)
                                                   │
                                                   ▼
                                              客户端收到
                                              完整回答
```

**`while True` 循环的通俗解释**：
- 状态机维护一个无限循环（`while True`）
- 每次循环检查 `self.current_state`（当前状态变量）
- 根据当前状态调用对应的处理函数（handler）
- 处理函数完成后，将 `self.current_state` 设为下一个状态
- 下一轮循环进入新状态
- 当状态变为 POST_PROCESSING 并完成处理 → `break` 退出循环

**为什么用这种设计**？因为 LLM 可能多次调用（对话可能需要多轮推理），每次 LLM 返回后需要根据结果决定下一步。用状态机模式比硬编码的 if-else 链更清晰易扩展。

### `yield` 关键字的通俗解释

这是 Python 初学者最容易困惑的概念。简单来说：
- 普通函数 (`return`)：一次性计算完所有结果，打包返回
- 生成器函数 (`yield`)：每次只产生一个结果，函数暂停，下次继续

```python
# 普通函数 - 一次性返回全部
def get_all():
    return [1, 2, 3]  # 内存中要同时保存 1,2,3

# 生成器函数 - 一个一个地返回
def get_one_by_one():
    yield 1  # 返回1，函数暂停
    yield 2  # 调用方要下一个时，返回2，函数暂停
    yield 3  # 再下一个时，返回3
```

在 agent-b101 中，`yield` 用于 SSE 流式输出——每次只向客户端发送一个 chunk，不需要等待完整回答生成完毕。
